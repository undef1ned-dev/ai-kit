Реализуй фичу через цепочку агентов профиля.

Фича: $ARGUMENTS

Флаги в начале задачи:
- `--worktree` — кодер, тестировщик и ревьюер работают в отдельном git worktree; рабочая папка пользователя не меняется, пока он не одобрит результат (шаг 8);
- `--tdd` — тестировщик пишет падающие тесты до кода (шаг 2а), кодер делает так, чтобы они прошли.

## Шаг 0 — Контракт профиля

Прочитай `.aikit/profiles.json`. Для каждого профиля в `profiles` там есть:
- `role` и `stack` — за какую часть системы отвечает профиль;
- `agents` — агенты по ролям `architect`, `coder`, `tester`, `reviewer`;
- `specialists` — дополнительные агенты и условие `when`, при котором их звать;
- `pipelines` — другие цепочки профиля, кроме кода (например, модели и текстуры): условие `when` и агенты `steps` по порядку;
- `root` — папка профиля в проекте (`.` — корень репозитория, `frontend` — Nuxt-приложение в `frontend/`);
- `commands` — команды проекта `install`, `lint`, `format`, `test`, `build`, `run` (`{files}` — изменённые файлы);
- `path_signals` — пути внутри `root`, по которым задача относится к профилю.

Если кит стоит плагинами Claude Code (есть `.aikit/plugin-init.json`), агент профиля запускается с префиксом плагина — имени профиля: `<профиль>:<агент>`.

Если файла нет — скажи, что AIKit не подключён к проекту (`/aikit:setup` при установке плагинами, иначе `attach.sh` или установщик адаптера), и остановись.

Выбери профиль задачи:
- явные пути в задаче сравни с `root` и `path_signals` (`frontend/pages/index.vue` — профиль с `root: frontend` и сигналом `pages/`);
- без путей — сопоставь задачу с `role` и `stack`;
- профиль один — бери его.

Если задача затрагивает несколько профилей (например, новый эндпоинт и страница, которая его использует), пройди цепочку по каждому: сначала профиль с `role: backend` — он фиксирует API-контракт, затем остальные. ARCHITECT_PLAN backend-профиля передай архитектору следующего профиля.

Если профиль неочевиден — спроси пользователя, не угадывай.

Сверь задачу с `pipelines` выбранного профиля:
- задача целиком подходит под `when` пайплайна и не меняет код — пройди только этот пайплайн (раздел «Пайплайн профиля») и заверши итогом;
- фиче нужен и код, и результат пайплайна — пройди цепочку кода, а пайплайн запусти в шаге 2;
- не подходит ни один — обычная цепочка кода.

## Рабочая папка

Без `--worktree` рабочая папка WORKDIR — корень проекта.

С `--worktree`:
1. Проверь, что проект — git-репозиторий (`git rev-parse --show-toplevel`). Если нет — скажи об этом и работай в корне проекта.
2. Придумай короткое имя латиницей по задаче: `notifications-filters`.
3. Создай worktree от текущего коммита:
   - `mkdir -p .aikit/worktrees`, и если нет `.aikit/worktrees/.gitignore` — запиши в него `*` (worktree не попадёт в `git status` проекта);
   - `git worktree add .aikit/worktrees/<имя> -b ai/<имя>`.
4. Если `git status --porcelain` в корне проекта не пустой — предупреди: незакоммиченных правок пользователя в worktree нет, фича строится от последнего коммита.
5. В папке `root` каждого профиля задачи внутри worktree выполни команду `install` из контракта — без зависимостей линтер и тесты не запустятся. Нет `install` — спроси пользователя, как поставить зависимости.
6. Файлы `.env` в worktree не копируй. Если тестам или запуску нужны переменные окружения — попроси пользователя положить их сам.

WORKDIR = `.aikit/worktrees/<имя>`. Каждому агенту назови WORKDIR: он читает и пишет файлы только в нём, а команды профиля запускает в `<WORKDIR>/<root>`.

## Шаг 1 — Архитектура (`agents.architect`)

Если задача идёт от макета (ссылка на Figma, фрейм, скриншот) и подходит под `when` одного из `specialists`, запусти этого специалиста до архитектора:
- передай ему задачу и ссылку на макет;
- он загружает макет через Figma MCP, подбирает компоненты UI kit и токены, отмечает, чего в UI kit не хватает, и возвращает implementation brief;
- brief передай архитектору вместе с задачей; в шаге 2 этого специалиста снова не зови.

Если Figma MCP недоступен или макет не загрузился — скажи пользователю, что сверки с живым макетом не было, и работай по тому, что есть.

Запусти архитектора профиля, назови ему WORKDIR и `root` профиля — пути плана считаются от `<WORKDIR>/<root>`:
- прочитай PRODUCT.md, CLAUDE.md и похожий код проекта;
- спроектируй минимальный набор изменений;
- выведи ARCHITECT_PLAN.

Дождись результата.

## Шаг 2 — Специалист (если нужен)

Если задача или ARCHITECT_PLAN подходит под условие `when` одного из `specialists`, которого ещё не звали в шаге 1:
- запусти агента специалиста с ARCHITECT_PLAN;
- его вывод передай кодеру, затем тестировщику и ревьюеру.

Специалист дополняет цепочку, а не заменяет её.

Если фиче нужен результат пайплайна профиля (шаг 0) — пройди его здесь с ARCHITECT_PLAN на входе, а итог передай кодеру.

## Пайплайн профиля

Запускай агентов из `steps` по очереди. Каждому передай задачу и выходной блок предыдущего агента (`output_block` из его frontmatter). Если агент вернул вопросы — остановись и уточни у пользователя.

## Шаг 2а — Тесты до кода (только `--tdd`, `agents.tester`)

Запусти тестировщика профиля с ARCHITECT_PLAN вместо CODER_RESULT:
- напиши тесты на поведение из плана: успешный сценарий, ошибки, граничные случаи;
- кода фичи ещё нет — не пиши его и не делай заглушек;
- выведи TESTER_RESULT.

Выполни команду `test` профиля. Тесты должны упасть, потому что фичи нет. Если они проходят или падают по другой причине (ошибка в самом тесте, не настроено окружение) — верни тестировщику с выводом команды.

## Шаг 3 — Реализация (`agents.coder`)

Запусти кодера профиля с ARCHITECT_PLAN:
- реализуй все файлы по плану;
- выведи CODER_RESULT.

С `--tdd` передай кодеру и TESTER_RESULT: задача — чтобы тесты прошли. Тесты кодер не меняет; если считает тест неверным — пусть вернёт вопрос.

Дождись результата.

## Шаг 4 — Тесты, ревью и линтер параллельно

Запусти одновременно, не дожидаясь одного перед другим:
- тестировщика профиля — тесты по CODER_RESULT (с `--tdd` — только дописать то, чего не хватило);
- ревьюера профиля — проверка CODER_RESULT: сначала общий проход (корректность, ошибки на краях и в обработке ошибок, безопасность), затем чек-лист профиля.

Как запустить параллельно:
- Claude Code — оба сабагента в фоне;
- Codex — попроси запустить обоих агентов и дождаться обоих;
- OpenCode — два вызова сабагентов в одном сообщении.

Пока они работают:
- выполни `lint` и `format` профиля на файлах из CODER_RESULT в `<WORKDIR>/<root>` (подставь их пути относительно `root` вместо `{files}`);
- общий ревью-шаг: в Claude Code запусти встроенный скилл `code-review` на изменениях (с `--worktree` — на папке WORKDIR). Он ищет ошибки корректности, ревьюер профиля добавляет к нему свой чек-лист. Если скилл недоступен, а также в Codex и OpenCode, общий проход делает ревьюер профиля.

Дождись тестировщика и ревьюера.

## Шаг 5 — Проверка командами профиля

Выполни `test` профиля в `<WORKDIR>/<root>`. Команды проекта могут отличаться от дефолтов кита — используй именно те, что в `.aikit/profiles.json`.

## Шаг 6 — Исправления

Если есть что исправлять:
- CRITICAL или `VERDICT: REQUEST_CHANGES` в REVIEW_RESULT;
- ошибки корректности от `code-review`;
- упали `lint` или `test`.

Тогда верни задачу кодеру с замечаниями и выводом команд. Если тест неверен — тестировщику. После исправлений снова выполни `lint` и `test`; ревьюер проверяет только исправленное.

Не больше двух кругов исправлений. Если после второго что-то осталось — остановись и покажи пользователю, что именно.

## Шаг 7 — Проверка в работе

Если в контракте профиля есть `run` — пройди скилл `check-feature` для этой фичи в WORKDIR: запустить приложение и проверить сценарий фичи (у профиля с UI — в браузере). Пропусти, если пользователь просил без запуска.

## Шаг 8 — Перенос из worktree (только `--worktree`)

1. Покажи, что изменилось: `git -C <WORKDIR> status --short`.
2. Спроси пользователя, переносить ли изменения в рабочую папку проекта. Не переносит — оставь worktree и скажи, где он лежит.
3. Перенос:
   - `git -C <WORKDIR> add -A`;
   - `git -C <WORKDIR> diff --cached --binary --output=../<имя>.patch` — файл пишет сам Git, путь считается от WORKDIR, патч ляжет в `.aikit/worktrees/<имя>.patch`. Не перенаправляй вывод через `>`: Windows PowerShell 5.1 запишет патч в UTF-16, и `git apply` его не прочитает;
   - в корне проекта `git apply .aikit/worktrees/<имя>.patch`. Если не применяется из-за незакоммиченных правок пользователя — `git apply --3way` и покажи конфликты.
4. Спроси, удалить ли worktree и ветку. Да — `git worktree remove --force <WORKDIR>`, `git branch -D ai/<имя>` и удали `.patch`.
