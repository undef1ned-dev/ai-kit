Зафиксируй командную память после задачи. Диалог ведёшь ты сам, в этом разговоре: агент `memory-writer` работает отдельно, историю разговора не видит и спросить пользователя не может — он получает уже подтверждённые записи, раскладывает их по `.aikit/memory/` и возвращает блок `MEMORY_RESULT`. Git после записи тоже делаешь ты.

Что зафиксировать: $ARGUMENTS

## Шаг 1 — Что записать

Собери из этого разговора и аргумента то, что пригодится команде и её агентам в следующих задачах:
- **решения** — что не очевидно из кода: почему этот подход, что отклонили;
- **паттерны**, которые стоит повторять;
- **коррекции агентов** — что агент сделал не так в этом проекте и как правильно;
- **модуль**, если запись касается одного модуля.

Отсей то, что не командная память: личные предпочтения одного разработчика (им место во встроенной памяти runtime), историю задачи «что сделано» (она в git и PR), то, что видно из кода, конфигов и `CLAUDE.md` / `AGENTS.md`, секреты, токены, адреса внутренних систем и персональные данные.

Задача описана в разговоре достаточно — не задавай вопросы, покажи, что понял, и дождись ответа:

> **Понял из контекста:**
> - Решения: ...
> - Паттерны: ...
> - Коррекции агентов: ...
> - Модуль: ...
>
> **Записать так? Или что-то поправить?**

Контекста недостаточно — задай вопросы одним блоком:

> **Зафиксирую командную память. Несколько быстрых вопросов:**
>
> **1. Какие решения приняли?** *(что не очевидно из кода: почему этот подход, что отклонили)*
>
> **2. Есть ли паттерн, который стоит повторять?**
>
> **3. Нужно ли скорректировать поведение какого-то агента?** *(например: «архитектор предложил лишний слой, в этом проекте его нет»)*
>
> *(Пункты можно пропускать, если нечего добавить)*

После фильтра ничего не осталось — скажи, что записывать нечего, и остановись. Пустая запись хуже никакой.

## Шаг 2 — Запись

Запусти агент `memory-writer` и передай подтверждённые записи, модуль и задачу, после которой они появились. Он создаст или обновит файлы в `.aikit/memory/`, обновит `INDEX.md` и вернёт `MEMORY_RESULT`.

Если агент вернул `QUESTIONS` — задай их пользователю одним сообщением, дождись ответов и запусти `memory-writer` снова: те же записи плюс ответы. Повторных вопросов обычно нет; если они пришли снова — ещё один круг, не больше.

`FILES` пустой — покажи, что отсеяно (`SKIPPED`), и остановись.

## Шаг 3 — Как сохранить в git

Покажи изменённые файлы (`git status --short .aikit/memory/`) и спроси:

> **Как сохранить память?**
> 1. **Оставить в рабочей папке** — войдёт в твой коммит и PR вместе с задачей *(по умолчанию)*
> 2. **Отдельный коммит** в текущей ветке
> 3. **Отдельная ветка и PR** на ревью команде

Сообщение коммита для 2 и 3 — по режиму коммитов из скилла `git-commit` (поле `commit` в `.aikit/settings.json`): `ask` — предложи варианты из `COMMIT` и дождись выбора, `auto` — коммить первым вариантом и покажи хеш.

**1** — ничего не делай с git, переходи к итогу.

**2** — `git add .aikit/memory/` и коммит: `docs(memory): <что зафиксировано>`.

**3** — отдельная ветка и PR:

```bash
BRANCH="docs/memory-$(date +%Y-%m-%d)-{slug}"
git switch -c "$BRANCH"
git add .aikit/memory/
git commit -m "docs(memory): {что зафиксировано}"
git push -u origin "$BRANCH"
```

Затем открой PR по хостингу из `git remote get-url origin`, описание — `PR_BODY`:
- **GitHub** — `gh pr create --title "docs(memory): …" --body-file <файл>`; ревьюер — `--reviewer <login>`, если он известен (строка `reviewer:` в `PRODUCT.md` или пользователь его назвал);
- **GitLab** — `glab mr create --title "docs(memory): …" --description "…"`, если `glab` установлен;
- нет `gh` / `glab` или они не авторизованы — дай ссылку на создание PR/MR (GitHub: `https://github.com/<owner>/<repo>/pull/new/<branch>`, GitLab: `<url>/-/merge_requests/new?merge_request[source_branch]=<branch>`) и текст описания.

После PR вернись на исходную ветку (`git switch -`), если пользователь не попросил иначе.
