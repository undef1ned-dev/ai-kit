## Исполнение в Codex

Задачу и флаги бери из текущего сообщения пользователя. Прочитай `AGENTS.md`, `PRODUCT.md` и `.aikit/profiles.json`, если они относятся к задаче. Для команд профиля используй его `root` и переопределённые `commands`, а не команды, выбранные по названию стека. Пользовательские инструкции имеют приоритет над рекомендациями скилла.

Если шаг требует субагента, используй локальное имя из `.codex/agents/*.toml` без префикса плагина. Предпочитай загруженную именованную роль. Если инструмент не умеет выбирать роль, передай доступному субагенту её `developer_instructions` и нужный контекст; передавай настройки модели только когда это поддерживается схемой инструмента. Не утверждай, что модель из TOML применена, если выбранный способ запуска её не применяет. Если инструменты делегирования недоступны, останови цепочку с объяснением, а не выдавай работу основного потока за запуск агентов.

Независимых тестировщика и ревьюера запускай до ожидания любого из них, затем дождись обоих; исправления передавай уже запущенному агенту доступным инструментом продолжения, если он есть. Лимит параллельности соблюдай. Не создавай пользовательские чаты вместо субагентов. Ключи и параметры запуска инструментов бери из фактической схемы текущей сессии.

Вопросы пользователю задаёт основной поток, а не субагент. Неполный или прерванный результат агента не считай успехом. Модель сама по себе не заменяет запуск проверок: в итог включай реально выполненные команды и их результаты. Операции git выполняй по скиллам `git-branch` и `git-commit`, учитывая режим команды и прямые указания пользователя.

Создай нового агента. Интервью ведёшь ты сам, в этом диалоге: агент `agent-builder` работает отдельно и спросить пользователя не может, поэтому он получает уже готовые ответы.

## Шаг 0 — Где запущено

Определи режим по корню рабочей папки:

- **кит** — есть `base/codex/agents/`, `profiles/` и `scripts/build-plugins.py`. Создаём агента кита. Для сложных правок кита основной путь — `/improve-aikit` (агент `aikit-maintainer`).
- **проект** — этих признаков нет. Создаём локального агента только для этого проекта, в кит он не попадает.

В режиме проекта ещё:
- **runtime** — Codex; создавай независимый нативный источник. Поддержку других runtime обсуждай отдельно, если пользователь её запросил;
- **профиль** — из `.aikit/profiles.json`, если файл есть: стек и стиль подскажут примеры и правила.

## Шаг 1 — Интервью

Задавай вопросы фазами, по одной фазе за сообщение, и жди ответов. Расплывчатый ответ — уточни, не двигайся дальше. Что уже есть в назначении агента — не переспрашивай, а подтверди.

**Фаза 1 — Идентичность**
1. Имя в kebab-case: `docs-writer`, `db-migrator`, `api-designer`.
2. Роль одним предложением: что агент делает и чего НЕ делает. Пример: «Пишет тесты для сервисного слоя. Не меняет бизнес-логику».
3. Размещение:
   - кит — `base` (нужен во всех проектах), профиль или пак: перечисли папки `profiles/*/` и `packs/*/`, которые есть в ките, или новый профиль (`python3 scripts/new-profile.py`);
   - проект — только подтверди runtime из шага 0.
4. Модель — реальный идентификатор Codex и model_reasoning_effort. Ориентируйся на нативные TOML соседних ролей и требования задачи к качеству и расходу. Не выводи модель из имени роли или уровня другого runtime.

**Фаза 2 — Инструменты и контекст**
5. Возможности: чтение, запись, команды, браузер — по инструментам текущей сессии. Ограничения роли опиши в инструкции, разрешения наследуются от родителя.
6. Что агент читает перед работой: `PRODUCT.md`, правила проекта (`AGENTS.md`), `.aikit/profiles.json`, похожий код проекта, выходной блок другого агента (например `ARCHITECT_PLAN`).
7. MCP-серверы: перечисли подключённые в текущей сессии и `.codex/config.toml` или mcp.json слоя кита; иначе «не нужны».

**Фаза 3 — Алгоритм**
8. Шаги работы по порядку, минимум три.
9. Задаёт ли агент вопросы перед работой? Помни: запущенный как сабагент, он спросить не может — только вернуть вопросы вызвавшему.
10. Шаблоны кода или документов, которые агент обязан использовать, — пример или набросок.

**Фаза 4 — Правила качества**
11. Что обязательно в результате. Пример: «тест-файл рядом с реализацией».
12. Что запрещено. Пример: «не трогать существующие миграции».
13. Самопроверка перед завершением. Пример: «прогоняет линтер».

**Фаза 5 — Формат вывода**
14. Что создаёт агент: файлы (какие и куда), текст для следующего агента, отчёт.
15. Именованный выходной блок для цепочки (`ARCHITECT_PLAN`, `REVIEW_RESULT`) и его поля — или «не нужен».
16. Что агент выводит пользователю в конце.

**Фаза 6 — Интеграция**
17. Кто вызывает: пользователь, скилл, другой агент.
18. Кто работает до и после него, что передаётся.
19. Нужен ли скилл-обёртка — создадим отдельно через `$create-skill`.
20. Только в проекте: должен ли `$implement-feature` звать агента как специалиста профиля.

## Шаг 2 — Файл агента

Запусти агент `agent-builder` и передай ему режим, runtime (в проекте), профиль из `.aikit/profiles.json` и все ответы интервью. Он сверит имя с существующими агентами, изучит конвенции и вернёт блок `AGENT_FILE`, ничего не записывая.

Если в `AGENT_FILE` есть `QUESTIONS` или `CONFLICTS` — покажи их пользователю, получи ответ и запусти `agent-builder` снова с уточнёнными ответами.

## Шаг 3 — Превью и запись

Покажи пользователю путь и полное содержимое каждого файла из `AGENT_FILE` и спроси: записать или что-то изменить? Правки — снова через `agent-builder`.

После подтверждения запиши файлы по путям из блока. Существующий файл не перезаписывай без отдельного подтверждения.
