## Исполнение в Codex

Задачу и флаги бери из текущего сообщения пользователя. Прочитай `AGENTS.md`, `PRODUCT.md` и `.aikit/profiles.json`, если они относятся к задаче. Для команд профиля используй его `root` и переопределённые `commands`, а не команды, выбранные по названию стека. Пользовательские инструкции имеют приоритет над рекомендациями скилла.

Если шаг требует субагента, используй локальное имя из `.codex/agents/*.toml` без префикса плагина. Предпочитай загруженную именованную роль. Если инструмент не умеет выбирать роль, передай доступному субагенту её `developer_instructions` и нужный контекст; передавай настройки модели только когда это поддерживается схемой инструмента. Не утверждай, что модель из TOML применена, если выбранный способ запуска её не применяет. Если инструменты делегирования недоступны, останови цепочку с объяснением, а не выдавай работу основного потока за запуск агентов.

Независимых тестировщика и ревьюера запускай до ожидания любого из них, затем дождись обоих; исправления передавай уже запущенному агенту доступным инструментом продолжения, если он есть. Лимит параллельности соблюдай. Не создавай пользовательские чаты вместо субагентов. Ключи и параметры запуска инструментов бери из фактической схемы текущей сессии.

Вопросы пользователю задаёт основной поток, а не субагент. Неполный или прерванный результат агента не считай успехом. Модель сама по себе не заменяет запуск проверок: в итог включай реально выполненные команды и их результаты. Операции git выполняй по скиллам `git-branch` и `git-commit`, учитывая режим команды и прямые указания пользователя.

Оптимизируй командную память. Вопросы пользователю задаёшь ты сам, в этом диалоге: агент `memory-optimizer` работает отдельно и спросить пользователя не может — он делает то, что не удаляет записи, а на что нужно согласие, возвращает в поле `QUESTIONS` блока `MEMORY_OPTIMIZATION`. Git после оптимизации тоже делаешь ты.

Что оптимизировать: (задача из сообщения пользователя)

## Шаг 1 — Оптимизация

Запусти агент `memory-optimizer` и передай ему аргумент. Он проверит пороги, перенесёт решения из логов задач прежних версий, объединит дубли, сожмёт `INDEX.md` и вернёт `MEMORY_OPTIMIZATION`.

`CHANGES: оптимизация не требуется` — скажи об этом и остановись.

## Шаг 2 — Согласие

`QUESTIONS` не «нет» — покажи `CHANGES` и задай вопросы одним сообщением: удалить ли `tasks/` после переноса, какие личные записи убрать (с их текстом — пользователь перенесёт его в свою встроенную память runtime). Без согласия ничего не удаляй.

Согласился хотя бы на что-то — запусти `memory-optimizer` снова и передай, на что дано согласие. Он сделает только это и вернёт блок заново. Ещё один круг, не больше.

## Шаг 3 — Как сохранить в git

Покажи изменённые файлы (`git status --short .aikit/memory/`) и спроси:

> **Как сохранить память?**
> 1. **Оставить в рабочей папке** — войдёт в твой коммит и PR *(по умолчанию)*
> 2. **Отдельный коммит** в текущей ветке
> 3. **Отдельная ветка и PR** на ревью команде

Сообщение коммита для 2 и 3 — по режиму коммитов из скилла `git-commit` (поле `commit` в `.aikit/settings.json`): `ask` — предложи варианты из `COMMIT` и дождись выбора, `auto` — коммить первым вариантом и покажи хеш.

**1** — ничего не делай с git, переходи к итогу.

**2** — `git add -A .aikit/memory/` и коммит.

**3** — ветка `docs/memory-optimize-$(date +%Y-%m-%d)`: `git switch -c`, `git add -A .aikit/memory/`, коммит, `git push -u origin <ветка>`. PR по хостингу из `git remote get-url origin`, описание — `PR_BODY`: GitHub — `gh pr create`, GitLab — `glab mr create`; нет `gh` / `glab` или они не авторизованы — ссылка на создание PR/MR и текст описания. После PR вернись на исходную ветку (`git switch -`), если пользователь не попросил иначе.
