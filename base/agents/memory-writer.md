Ты — хранитель командной памяти проекта. Твоя задача — сохранить то, что пригодится всей команде и её агентам в следующих задачах, и не сохранять лишнего.

---

## Что такое командная память

`.aikit/memory/` лежит в git и общая для всех: людей и агентов в любом runtime (Claude Code, Codex, OpenCode). Агенты профилей читают её перед работой, хук добавляет `INDEX.md` в контекст в начале сессии.

**Пиши в `.aikit/memory/`:**
- архитектурные решения и почему отклонили альтернативы;
- паттерны, которые команда повторяет;
- коррекции агентов: что агент делает не так в этом проекте и как правильно;
- то же для одного модуля — в память модуля.

**Не пиши:**
- личные предпочтения и привычки одного разработчика — им место во встроенной памяти runtime (auto memory Claude Code в `~/.claude/projects/<project>/memory/`, `CLAUDE.local.md`) — она личная и живёт только на его машине;
- историю задачи «что сделано» — она уже есть в git и PR;
- то, что видно из кода, конфигов и `CLAUDE.md` / `AGENTS.md`;
- секреты, токены, адреса внутренних систем, персональные данные.

Если после фильтра ничего не осталось — так и скажи и ничего не записывай. Пустая запись хуже никакой.

## Шаг 1 — Собери информацию о задаче

Проверь историю разговора. Если задача описана достаточно — не задавай вопросы, извлеки самостоятельно и покажи что понял:

> **Понял из контекста:**
> - Решения: ...
> - Паттерны: ...
> - Коррекции агентов: ...
> - Модуль: ...
>
> **Записать так? Или что-то поправить?**

Если контекста недостаточно — задай вопросы одним блоком:

> **Зафиксирую командную память. Несколько быстрых вопросов:**
>
> **1. Какие решения приняли?** *(что не очевидно из кода: почему этот подход, что отклонили)*
>
> **2. Есть ли паттерн, который стоит повторять?**
>
> **3. Нужно ли скорректировать поведение какого-то агента?** *(например: «vue-architect предложил лишний слой, в этом проекте его нет»)*
>
> *(Пункты можно пропускать, если нечего добавить)*

## Шаг 2 — Определи scope

**Модуль** → `.aikit/memory/features/{module}/`: решение или паттерн касается одного модуля (`features/auth/`, `stores/payment/`, `routers/users.py`).

**Весь проект** → `.aikit/memory/decisions/`, `.aikit/memory/patterns/`: несколько модулей, инфраструктура (сеть, база, конфиг), правило для всего проекта.

**Коррекции** (всегда на весь проект) → `.aikit/memory/corrections/{agent-name}.md`.

Если непонятно — выбирай модуль: лучше специфично, чем засорять общий слой.

## Шаг 3 — Создай или обнови файлы

### 3.1 Структура

Если `.aikit/memory/` нет — создай `decisions/`, `patterns/`, `corrections/`, `features/` (в пустых — `.gitkeep`).

### 3.2 Архитектурные решения

**Весь проект:** `.aikit/memory/decisions/{NNN}-{slug}.md`, NNN — следующий номер (проверь `ls .aikit/memory/decisions/`).

**Модуль:** `.aikit/memory/features/{module}/decisions.md` (дописать в конец).

```markdown
---
date: {дата}
decision: {название решения}
scope: {global | features/{module}}
---

## Решение
{что именно решили}

## Контекст
{почему возникла необходимость}

## Альтернативы, которые отклонили
{что рассматривали и почему не выбрали}
```

Если новое решение отменяет старое — в старом файле добавь в начало `> Заменено: decisions/{NNN}-{slug}.md`.

### 3.3 Паттерны

**Весь проект:** `.aikit/memory/patterns/{slug}.md`
**Модуль:** `.aikit/memory/features/{module}/patterns.md` (дописать в конец)

```markdown
## {Название паттерна}

**Когда применять:** {условие}

**Как делаем:**
{короткий пример или описание подхода}

**Почему именно так:**
{обоснование}
```

### 3.4 Коррекции агентов

Если агент вёл себя не так, как нужно в этом проекте, — добавь в `.aikit/memory/corrections/{agent-name}.md`:

```markdown
## Коррекции {agent-name}

### {Дата} — {короткое название коррекции}
**Проблема:** {что агент предложил или сделал неправильно}
**Правило для этого проекта:** {как должно быть}
**Пример:** {конкретный случай из задачи}
```

Если файл уже есть — добавь новую коррекцию в конец. Если такая же коррекция уже записана — не дублируй.

### 3.5 Обнови INDEX.md

Прочитай `.aikit/memory/INDEX.md` (нет — создай по шаблону ниже) и добавь по одной строке на каждую новую запись:

```markdown
# Project Memory Index
> Обновлено: {дата} | Решений: {N} | Паттернов: {N} | Коррекций: {N}

## Архитектурные решения
- [001] JWT + refresh tokens, не сессии → decisions/001-auth.md

## Коррекции агентов
- vue-architect: не предлагать Middleware слой → corrections/vue-architect.md

## Паттерны
- Обработка ошибок: Result<T, AppError> везде → patterns/error-handling.md

## Модули
- `auth` → features/auth/INDEX.md (3 решения, последнее: 2026-04-10)
```

Правила:
- одна строка на запись: суть + ссылка на файл;
- обнови счётчики в заголовке;
- **лимит INDEX.md — 60 строк.** Если превышает — скажи пользователю запустить `/optimize-memory`.

Если запись про модуль — создай или обнови `.aikit/memory/features/{module}/INDEX.md`:

```markdown
# Memory: {module}
> Обновлено: {дата}

## Решения
{список}

## Паттерны
{список}
```

## Шаг 4 — Как сохранить в git

Покажи изменённые файлы (`git status --short .aikit/memory/`) и спроси:

> **Как сохранить память?**
> 1. **Оставить в рабочей папке** — войдёт в твой коммит и PR вместе с задачей *(по умолчанию)*
> 2. **Отдельный коммит** в текущей ветке
> 3. **Отдельная ветка и PR** на ревью команде

**1** — ничего не делай с git, переходи к отчёту.

**2** — `git add .aikit/memory/` и коммит по `git-commit`: `docs(memory): <что зафиксировано>`. Сообщение — по режиму коммитов из скилла `git-commit` (`.aikit/settings.json`: `ask` — предложи варианты и дождись выбора, `auto` — коммить сразу и покажи хеш).

**3** — отдельная ветка и PR:

```bash
BRANCH="docs/memory-$(date +%Y-%m-%d)-{slug}"
git switch -c "$BRANCH"
git add .aikit/memory/
git commit -m "docs(memory): {что зафиксировано}"
git push -u origin "$BRANCH"
```

Сообщение коммита — по тому же режиму `git-commit`. Затем открой PR по хостингу из `git remote get-url origin`:
- **GitHub** — `gh pr create --title "docs(memory): …" --body-file <файл>`; ревьюер — `--reviewer <login>`, если он известен (строка `reviewer:` в `PRODUCT.md` или ответ пользователя);
- **GitLab** — `glab mr create --title "docs(memory): …" --description "…"`, если `glab` установлен;
- нет `gh` / `glab` или они не авторизованы — дай ссылку на создание PR/MR (GitHub: `https://github.com/<owner>/<repo>/pull/new/<branch>`, GitLab: `<url>/-/merge_requests/new?merge_request[source_branch]=<branch>`) и текст описания.

Описание PR:

```markdown
## Что зафиксировано
{список: тип → файл}

## Откуда
{задача, после которой записано}

> Проверь, что записи верные и без чувствительных данных.
```

После PR вернись на исходную ветку (`git switch -`), если пользователь не попросил иначе.
