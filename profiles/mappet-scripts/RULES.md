# Mappet Scripts — правила проекта

## Источники и область работы

- Работай в `root` профиля из `.aikit/profiles.json`. Читай `tsconfig.json`, ближайший аналог в `src/`, нужный раздел `docs/` и `docs/AGENTS.md`, если он есть. Пути ниже даны относительно корня скриптов.
- Игровые сценарии входят через глобальные функции из обработчиков и GUI, используют классы из `src/classes/`, библиотеки из `src/libs/`, доменные декларации из `src/@types/` и общие значения из `src/utils/constants.ts`.
- `tsc` компилирует TypeScript в ES5. Сохраняй совместимость с целевым Rhino на Java 8. Сверяй Java interop, наличие методов и перегрузки с `src/@types/mappet.d.ts`, рабочими вызовами проекта и исходниками установленной версии мода. Официальная документация Mappet поясняет базовый API.
- Сохраняй глобальные runtime-имена и точку входа соседних скриптов. Используй ambient-декларации. Избегай runtime-импортов, `require` и синтаксиса модуля, который меняет область видимости скомпилированного скрипта. ES5 emit не добавляет полифилы. Для новых методов стандартной библиотеки и Java-коллекций сначала проверь поддержку на целевом движке.

## Стиль TypeScript

- Пиши исходники для чтения. Соблюдай отступ в два пробела и пустые строки между полями, методами и смысловыми блоками внутри методов: проверки, подготовка, изменение состояния, логирование, последствия. Длинные цепочки и объекты раскладывай по строкам. Production-сборка минифицирует код.
- Имена и JSDoc нового кода пиши на английском по общим правилам AIKit. Игровой текст, сообщения логов и документацию проекта пиши на русском, в терминологии соседней механики.
- Добавляй короткий JSDoc каждому новому или изменённому классу, полю, конструктору, методу, функции, интерфейсу, его полям, объявлению типа и константе. Описывай назначение и контракт. Раскрывай параметры, возвращаемые значения и инварианты по необходимости. Многострочный алгоритм объясняй для действительно сложной логики.
- Явно типизируй поля, параметры, результаты, локальные значения и callback там, где требуется контракт. Имена интерфейсов начинай с `I`, алиасов с `T`, перечислений с `E`. Структуры данных и сложные сигнатуры выноси в именованные интерфейсы и типы соответствующего `src/@types/<domain>.d.ts`, включая результаты методов, параметры callback и временный стейт GUI. Используй существующие контракты. Избегай `any`, двойных приведений и принудительного разыменования. Для пойманной ошибки используй `unknown` и проверенный проектный путь логирования.
- Явно ставь `public` или `private` на поля и методы класса по их фактической видимости. Для новых фиксированных строк и чисел используй именованные типизированные константы или существующие enum. Общие ключи, цвета, ID, размеры и настройки добавляй к подходящей группе констант, локальные значения оставляй рядом с механизмом. Динамические значения вычисляй из данных и констант.
- Для одного возвращаемого выражения используй краткую стрелку, для объекта — `item => ({ ... })`, для последовательности действий — блок. Используй готовые данные и прямые объекты полей. Сохраняй формулы, порядок действий, расход предметов, число бросков и момент каждого броска при правках инфраструктуры. Ограничивай diff задачей.

## Данные, метаданные и логирование

- Новый `EPlayerStates` согласуй с `IPlayerData` в `src/@types/player.d.ts`, `Player.getDataFromStates()` и схемой `PlayerSchemaValidator`, включая дефолты раздела. Иначе валидация при входе удалит или сбросит состояние.
- При добавлении исполняемого файла или изменении глобальных вызовов сверяй world-side `<script>.js.json`. Список `Libraries` плоский: включи прямые глобальные вызовы и зависимости фактически вызванных методов, в порядке загрузки. Сохраняй SNBT-флаги `Unique: 1b` и текущее значение `GlobalLibrary` (для нового скрипта обычно `0b`). `utils/common.js` и `utils/constants.js`, когда нужны оба, следуют в конце в этом порядке по конвенции проекта. `.d.ts` метаданных не требует. При отсутствии world-каталога укажи точный относительный путь и требуемый список в результате.
- Боевые события идут через `combat.logger`, реализация `CombatLogger` находится рядом с `CombatGui` в `Combat.ts`. Сохраняй сигнатуру `log(event, fields, level = ELogLevel.Info, trace?)` и существующие enum категорий, уровней, событий и проверок навыков.
- Для логов новой проверки навыка используй уже рассчитанные ник/UUID, результат, исходный кубик, параметр и навык. При отсутствии порога оставляй `success = null`. Сохраняй один дополняемый UUID-файл на бой, синхронные переходы боя, общую ротацию прочих категорий и очистку по сроку и квотам. Формат событий обходится без `v`, `run` и `seq`.

## GUI и проверка

- Экран поручай специалисту `gui` профиля. Выбирай образец по типу экрана в `src/gui/`. Используй `mappet-scripts-gui-builder` для жизненного цикла и `mappet-scripts-gui-layout` для разметки. После ввода из GUI перепроверяй право, фазу и актуальность данных на сервере непосредственно перед действием.
- Выполняй безопасную команду `test` из контракта, она проверяет TypeScript без записи в мир и запускает существующие combat/metadata сценарии. Для GUI укажи, какие действия проверены в Minecraft, и перечисли сценарии, которым ещё нужна игровая проверка.
- Штатные `build` и watch проекта выводят файлы в каталог мира Minecraft. Операции сборки с записью, обновления метаданных мира и reload выполняй только в явно согласованном окружении задачи. Для проверки типов достаточно `--noEmit`.
