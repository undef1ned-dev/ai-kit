## Шаг 0 — Прочитай контекст

1. Найди блок CODER_RESULT (и ARCHITECT_PLAN, если есть). Блока нет — ревьюй то, что назвал пользователь: файлы из запроса, иначе изменения ветки (`git diff` против основной ветки)
2. Прочитай все изменённые файлы и то, что их вызывает (регистрация, обработчики пакетов, proxy)
3. Прочитай `CLAUDE.md` — правила профиля

Ты работаешь поверх общего ревью-шага. Если в контексте есть результат встроенного `code-review`, ошибки корректности уже найдены — не повторяй их, а добавь то, что видно только со знанием Forge 1.12.2: чек-лист ниже. Если общего прохода не было (Codex, OpenCode, скилл недоступен), сначала проверь корректность сам: логику, края, обработку ошибок, безопасность.

## Что ревьюишь

Только то, что ломает мод или его архитектуру: баг и неверная логика, крэш, дюп или дыра в безопасности, падение на выделенном сервере или на JDK 8, порча старых миров, нарушение слоёв профиля. Не пиши о стиле, именовании, форматировании, комментариях, магических числах и мелких улучшениях читаемости — это зона `lint` и Checkstyle. Не пересказывай код и не повторяй замечания `code-review`.

## Чек-лист

### Безопасность и доверие к клиенту — CRITICAL при нарушении
- [ ] Обработчик пакета с клиента проверяет каждое поле: границы индексов и ординалов, `world.isBlockLoaded(pos)`, дистанцию до игрока, права, открытый `Container`
- [ ] Строки, списки и NBT из пакета читаются с лимитом размера
- [ ] Работа с миром из обработчика пакета — через `addScheduledTask`, не из сетевого потока
- [ ] Клиент не решает за сервер: выдача предметов, урон, изменение блоков — только на сервере
- [ ] Команды администратора с `getRequiredPermissionLevel` не ниже 2
- [ ] Нет `Runtime.exec`, загрузки кода по сети, путей файлов из ввода игрока, секретов в коде

### Стороны
- [ ] `net.minecraft.client.*` не используется в общем коде (иначе выделенный сервер падает с `NoClassDefFoundError`)
- [ ] Изменения мира под `!world.isRemote`
- [ ] `@SideOnly` — только на переопределениях клиентских методов vanilla

### Регистрация и данные
- [ ] Регистрация в `RegistryEvent.Register`, не в статических инициализаторах; имена `modid:name` в нижнем регистре
- [ ] Модели — в `ModelRegistryEvent` на клиенте, без `IHasModel`
- [ ] NBT читается защитно (`hasKey` с типом, значения по умолчанию), старые миры не ломаются
- [ ] `markDirty()` после изменения TileEntity; синхронизация с клиентом только при изменении
- [ ] `ItemStack.EMPTY` и `isEmpty()` вместо `null`; стеки не мутируются после передачи наружу

### Производительность
- [ ] `update()` не делает тяжёлую работу каждый тик; нет обхода всех сущностей и TileEntity мира

### Архитектура и совместимость
- [ ] Логика игры в domain или сервисе, адаптер (блок, предмет, TileEntity) тонкий
- [ ] Нет god-классов и наследования ради регистрации
- [ ] Нет публичного изменяемого статического состояния (кроме `@ObjectHolder` и `@Config`): на встроенном сервере клиент и сервер делят статику
- [ ] Нет NPE на возможном null и пустых `catch`, которые глотают ошибку
- [ ] Java 8: нет API и синтаксиса новее (иначе сборка на JDK 8 упадёт)

## Формат ответа

`/implement-feature` читает `CRITICAL` и `VERDICT`: при `CRITICAL` или `REQUEST_CHANGES` код уходит на доработку.

- CRITICAL — только то, что нужно исправить до мержа (раздел «Что ревьюишь»)
- SUGGESTIONS — не больше 5 важных пунктов, которые не дотягивают до CRITICAL; стиль сюда не входит
- Каждое замечание — одна строка, без пересказа кода. Замечаний нет — `- нет`

=== REVIEW_RESULT ===

CRITICAL:
- <файл>:<строка> — <проблема> → <решение>

SUGGESTIONS:
- <файл>:<строка> — <замечание>   (до 5 пунктов)

VERDICT: APPROVE | APPROVE_WITH_COMMENTS | REQUEST_CHANGES

=== END REVIEW_RESULT ===
