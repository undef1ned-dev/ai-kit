## Шаг 0 — Прочитай контекст

1. Найди блоки CODER_RESULT (TO_TEST) и ARCHITECT_PLAN (TEST_PLAN) в истории разговора. В режиме `--tdd` CODER_RESULT ещё нет — пиши тесты по TEST_PLAN, кода фичи не пиши
2. Прочитай изменённые классы, `build.gradle` (какой JUnit, есть ли Mockito) и существующие тесты в `src/test/java/` как образец
3. Пути — от `root` профиля `forge-1-12-java` в `.aikit/profiles.json`

## Что тестировать

Тесты — только на то, что дорого сломать: критичную логику, регрессии и нетривиальные ветки. Покрытие ради покрытия не нужно: один тест на каждое отдельное поведение или ветку, без копий, которые отличаются только данными. TEST_PLAN архитектора — ориентир: бери из него важное, а не всё подряд. Если пользователь сам назвал классы (`/forge-1-12-add-tests`) — покрой их поведение по тем же правилам.

- **domain** — основной слой: расчёты, правила, рецепты, переходы состояний; граничные значения и ошибки — там, где от них зависит результат
- **проверки пакетов** — логику валидации, вынесенную из `Handler`: выход за границы, чужая позиция, слишком далеко, слишком длинная строка — действие не выполняется
- **NBT** — чтение сохранённых данных: без ключа и с ключом другого типа даёт значение по умолчанию, старые миры читаются
- **регрессии** — исправленный баг или поведение, которое меняла задача; при рефакторинге без смены поведения главная проверка — существующие тесты, новые — только там, где рискованное поведение не покрыто
- **конфиг** — границы диапазонов, только если от значения зависит логика
- **код с реестром** (`Block`, `Item`, `ItemStack`) — только если без реестра не проверить: `Bootstrap.register()` в `@BeforeClass`

Не тестируй геттеры и сеттеры, конструкторы, константы, регистрацию, простое делегирование адаптера в domain, код без ветвлений и то, что уже покрыто существующими тестами. Не пиши тесты на сам Forge и vanilla. Если логика зашита в класс блока и без мира её не проверить — отметь это в GAPS как техдолг (логику нужно вынести в domain), а не мокай `World` целиком.

## Правила

- JUnit 4 (`org.junit.Test`, `Assert.*`) и Mockito, если они в проекте; JUnit 5 — только если `build.gradle` уже включает `useJUnitPlatform()`. Новые зависимости в `build.gradle` не добавляй — предложи в GAPS
- Тест называет поведение: `returnsEmptyStackWhenSlotOutOfRange`
- Без магических чисел: константы в тестовом классе
- Тестируй поведение, а не внутреннюю реализацию
- Запусти команду `test` профиля из `.aikit/profiles.json` в папке `root` профиля и приложи результат. Нет декомпилированного workspace — сначала `install` профиля; не запускается — так и напиши в RUN

## Ручной сценарий в игре

Только если задача меняет поведение, которое видно лишь в мире и unit-тестом не проверено (рендер, GUI, синхронизация с клиентом, выделенный сервер): опиши главное шагами для `./gradlew runClient` и `runServer` — что сделать и что должно произойти, не больше 5 шагов. Его пройдёт `/check-feature` или человек. Иначе — «не нужен».

GAPS — только существенные риски, которые остались без проверки, не больше 3 пунктов. Не перечисляй всё, на что не писал тесты.
