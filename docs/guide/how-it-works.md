# Как это работает

Что происходит между командой `/implement-feature` и готовым кодом: откуда runtime берёт агентов, как выбирается профиль и как агенты передают работу друг другу.

## Три слоя

<!-- chain -->
- **Источник** — `base/`, `profiles/`, `packs/` в репозитории AIKit: агенты, скиллы, правила, MCP описаны один раз
- **Доставка** — плагины маркетплейса `aikit` (Claude Code, Codex) или установщик `attach.sh` / `install-adapter-package.py` раскладывают их в формат конкретного runtime
- **Проект** — runtime читает плагины и файлы из своих папок: `.claude/`, `.agents/`, `.codex/`, `.opencode/`

Источник один, поэтому поведение одинаковое во всех runtime. При установке плагинами агенты, скиллы, хуки и MCP приходят из плагинов, а в проект пишутся только правила, контракты, память и настройки (в Codex — ещё агенты). Установщик кладёт всё в папки проекта — туда, где каждый runtime ищет файлы:

| Что | Claude Code | Codex | OpenCode |
|---|---|---|---|
| Правила проекта | `CLAUDE.md` | `AGENTS.md` | `AGENTS.md` |
| Скиллы | `.claude/skills/` | `.agents/skills/` | `.agents/skills/` |
| Агенты | `.claude/agents/*.md` | `.codex/agents/*.toml` | `.opencode/agents/*.md` |
| MCP-серверы | `.mcp.json` | `.codex/config.toml` | `opencode.json` |
| Контракты профилей | `.aikit/profiles.json` | `.aikit/profiles.json` | `.aikit/profiles.json` |
| Хуки | `hooks` в `.claude/settings.json` | `.codex/hooks.json` | плагин `.opencode/plugins/aikit-hooks.js` |

Подробная матрица с ограничениями — [Поддержка runtime](../runtime-support.md).

## Ядро не знает стеков

Главная идея устройства: общие сценарии (`/implement-feature`, `/security-check`) не содержат ни одного имени стека или агента профиля. Всё стековое они читают из `.aikit/profiles.json` — файла, куда установщик собрал [контракты](glossary.md#контракт-профиля) подключённых профилей.

Вот фрагмент такого файла для fullstack-проекта, где Nuxt живёт в `web/`, а бэкенд на Spring (профиль из примера [Как добавить стек](adding-a-stack.md)) — в `api/`:

```json
{
  "profiles": {
    "java-spring": {
      "role": "backend",
      "stack": "Java 21, Spring Boot 3, JUnit 5",
      "agents": {
        "architect": "spring-architect",
        "coder": "spring-coder",
        "tester": "spring-tester",
        "reviewer": "spring-reviewer"
      },
      "commands": { "lint": "./mvnw checkstyle:check", "test": "./mvnw test" },
      "path_signals": ["src/main/java/", "src/test/java/"],
      "root": "api"
    },
    "vue-nuxt": {
      "role": "web",
      "agents": { "architect": "vue-architect", "coder": "vue-coder", "tester": "vue-tester", "reviewer": "vue-reviewer" },
      "commands": { "lint": "npx eslint {files}", "test": "npx vitest run" },
      "path_signals": ["pages/", "components/", "stores/"],
      "root": "web"
    }
  }
}
```

Поэтому новый стек — это только новая папка в `profiles/`: ядро править не нужно. Как его добавить — [Как добавить стек](adding-a-stack.md).

## Что делает /implement-feature

<!-- steps -->
1. **Выбирает профиль.** Читает `.aikit/profiles.json`. Если в задаче есть пути, сравнивает их с `root` и `path_signals`: `web/pages/orders.vue` → профиль с `root: web` и сигналом `pages/`. Без путей сопоставляет задачу с `role` и `stack`. Если профиль один — берёт его. Если непонятно — спрашивает.
2. **Архитектор пишет план.** Агент `agents.architect` читает `PRODUCT.md`, `CLAUDE.md` и похожий код проекта и выводит `ARCHITECT_PLAN`: какие файлы создать и изменить, какие состояния и ошибки учесть, какие тесты нужны.
3. **Подключает специалиста или пайплайн, если нужно.** Если задача подходит под `when` одного из специалистов профиля, тот дополняет план. Если фиче нужен результат пайплайна, пайплайн идёт здесь.
4. **Кодер реализует план.** Агент `agents.coder` получает `ARCHITECT_PLAN` и выводит `CODER_RESULT` — список сделанного.
5. **Тестировщик, ревьюер и линтер работают одновременно.** `agents.tester` пишет тесты по `CODER_RESULT`, `agents.reviewer` сначала проверяет код на ошибки, затем по чек-листу профиля, а в это время запускаются `lint` и `format`. В Claude Code к ревью добавляется встроенный `/code-review`.
6. **Проверка тестами.** В папке `root` профиля запускается `test`.
7. **Исправления.** Если ревью нашло критичное или упала команда, задача возвращается кодеру (или тестировщику, если неверен тест). Не больше двух кругов, потом ассистент показывает, что осталось.
8. **Проверка в работе.** Если у профиля есть команда `run`, приложение запускается, и сценарий фичи проходится в браузере или запросами — это скилл `/check-feature`.
9. **Итог.** Ассистент показывает профиль и цепочку агентов, созданные файлы, результат тестов, ревью, проверку в работе и следующие шаги (миграции, ручные проверки).

На любом шаге агент может вернуть вопросы — тогда цепочка останавливается, пока ты не ответишь.

### Как агенты передают работу

Каждый агент выводит результат в оговорённом блоке, следующий получает этот блок на вход:

```text
=== ARCHITECT_PLAN ===
Профиль: vue-nuxt (root: web)
Создать:
  pages/notifications/index.vue — список, фильтр «непрочитанные», empty state
  stores/notifications.ts       — загрузка, markAllRead с optimistic update
Изменить:
  layouts/default.vue           — бейдж с количеством непрочитанных
Тесты: stores/notifications (markAllRead, откат при ошибке)
=== END PLAN ===
```

Кодер не придумывает архитектуру заново, а реализует план. Ревьюер сверяет код с планом и правилами. Так задача не расползается.

### Режимы: --tdd и --worktree

Флаги пишутся в начале задачи: `/implement-feature --tdd --worktree фильтр уведомлений`.

| Флаг | Что меняется |
|---|---|
| `--tdd` | После плана тестировщик пишет тесты на поведение из плана. Они должны упасть, потому что фичи ещё нет. Кодер делает так, чтобы тесты прошли, и сами тесты не меняет |
| `--worktree` | Агенты работают в отдельной копии репозитория — git worktree в `.aikit/worktrees/<имя>` на ветке `ai/<имя>` от текущего коммита. В ней ставятся зависимости (команда `install` профиля). Твоя рабочая папка не меняется, пока ты не согласишься перенести результат. После переноса ассистент спросит, удалить ли worktree |

`--worktree` полезен, когда в рабочей папке есть свои незаконченные правки или хочется спокойно отказаться от результата. Цена — установка зависимостей при каждом запуске. Твои незакоммиченные правки в worktree не попадают: он строится от последнего коммита.

### Если задача затрагивает несколько профилей

«Добавь эндпоинт заказов и страницу, которая их показывает» — работа и для бэкенда, и для фронтенда. `/implement-feature` проходит цепочку по каждому профилю: **сначала backend** — он фиксирует API-контракт, затем web. План бэкенд-архитектора передаётся фронтенд-архитектору, поэтому страница использует ровно тот API, который сделан.

## Специалисты и пайплайны

Четыре роли — обязательная цепочка кода. Кроме неё профиль может иметь два вида дополнительных агентов.

| | Специалист | Пайплайн |
|---|---|---|
| Что это | Один агент | Цепочка из нескольких агентов |
| Когда работает | Внутри цепочки кода, если задача подходит под `when` | Сам по себе, если задача целиком подходит под `when` и код не нужен; или внутри фичи после архитектора |
| Что даёт | Совет: уточняет план для кодера | Готовый результат (артефакт): модель, текстура, документ |
| Пример в ките | `vue-design-bridge`, `vue-quality-analyst` | Пока нет в профилях кита — пример ниже |

Примеры на гипотетическом профиле для модов Minecraft с пайплайном `asset` (арт-директор → моделлер → текстурщик → ревью ассетов):

| Задача | Что запустится |
|---|---|
| «Нарисуй текстуру для рубинового меча» | Только пайплайн `asset`: кода нет |
| «Добавь рубиновую руду: блок, генерация в мире, текстура» | Цепочка кода; пайплайн `asset` идёт после архитектора, кодер получает готовые пути к модели и текстуре |
| «Перепиши регистрацию блоков на DeferredRegister» | Только цепочка кода |
| «Сверь новый экран настроек с макетом» (профиль `vue-nuxt`) | Цепочка кода + специалист `vue-design-bridge` |

Как описать специалиста и пайплайн в своём профиле — [Как добавить стек](adding-a-stack.md#пайплайны-работа-кроме-кода).

## Баги и проверка в работе

`/fix-bug` чинит баг так, чтобы он не вернулся:

<!-- chain -->
- **Воспроизведение** — ассистент находит причину и пишет `BUG_REPORT`: симптом, файл и строка, как воспроизвести
- **Тест на баг** — тестировщик профиля пишет тест, который падает именно из-за бага
- **Фикс** — кодер делает минимальное исправление причины, тест не трогает
- **Проверка** — `lint`, весь `test`, ревьюер смотрит, нет ли того же бага рядом

`/check-feature` запускает приложение командой `run` из контракта и проходит сценарий фичи: в браузере (Playwright MCP или встроенный браузер runtime) для профиля с UI, запросами — для API. Смотрит ошибки в консоли и логах, в конце останавливает приложение. Ничего не чинит — только сообщает, работает ли.

## От идеи до кода

Для крупной фичи есть цепочка до разработки:

<!-- chain -->
- **/analyze-mvp** — разбирает идею: аудитория, варианты, риски; пишет документ в `docs/mvp/`
- **/implement-mvp** — превращает документ в технический план: API-контракт, BACKEND и WEB SCOPE, порядок работ
- **/implement-feature** — реализует каждую часть плана цепочкой агентов профиля

## Хуки — правила, которые соблюдаются всегда

Правило в `CLAUDE.md` модель обычно выполняет, но может и забыть. [Хук](glossary.md#хук) runtime запускает сам, на каждое событие. AIKit ставит четыре хука. Логика у них одна — скрипт `.aikit/hooks/aikit_hook.py`, а каждый runtime только вызывает его в своём формате.

| Когда | Что делает хук | Если правило нарушено |
|---|---|---|
| Перед командой или записью файла | Не даёт записать `.env` и секреты (ключи AWS, токены GitHub, приватные ключи…), добавить `.env` в git через `git add`, сделать коммит не по Conventional Commits или с `Co-Authored-By`, создать ветку не по Conventional Branch | Действие отменяется, агент получает причину и исправляет: переписывает сообщение коммита, берёт секрет из переменной окружения |
| После правки файла | Запускает `format` и `lint` профиля для изменённого файла — в папке `root` этого профиля | Замечания линтера сразу возвращаются агенту |
| Когда агент закончил ответ | Если менялся код профиля — запускает его `test` | Тесты упали — агент продолжает работу с их выводом. После крупной задачи (8+ файлов) предлагает `/capture-memory`, если у проекта есть `.aikit/memory/` |
| В начале сессии | Добавляет в контекст память команды `.aikit/memory/INDEX.md` и `PRODUCT.md`, если они заполнены | — |

Какие файлы считаются кодом профиля, задаёт поле `code_extensions` контракта: для `vue-nuxt` это `.vue`, `.ts`, `.js` и родственные, для Python-профилей — `.py`. Правка `README.md` линтер не запускает.

Хуки ничего не скачивают и не ломают работу: если инструмента нет (например, ESLint не установлен в проекте), хук молча пропускает линтер, а вместо тестов напоминает проверить их вручную. Если сам скрипт упал, действие проходит.

> [!NOTE]
> Команды хуки берут из `.aikit/profiles.json`. Поменял там `lint` или `test` под проект — хуки запускают уже твою команду.

## Как обновление сохраняет правки проекта

Команды и `root` в `.aikit/profiles.json` команда может поменять под себя: например, `pnpm vitest run` вместо `npx vitest run`. Чтобы обновление кита не затёрло такую правку, установщик хранит прежние значения кита в `.aikit/profiles.kit-defaults.json` и при обновлении сравнивает три версии:

| Значение в проекте | Что сделает обновление |
|---|---|
| Совпадает со старым значением кита (команда его не трогала) | Заменит на новое значение кита |
| Отличается от старого значения кита (команда поменяла) | Оставит как есть |
| Команда удалена в проекте | Не вернёт |
| Новая команда, которой раньше в ките не было | Добавит |
