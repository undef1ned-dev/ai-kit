# Термины

Словарь AIKit, от общих понятий AI-разработки к устройству кита. Если слово встретилось в документации и непонятно — ищи его здесь, поиск сайта тоже находит термины.

## Общие понятия

### Модель

Нейросеть, которая генерирует текст и код: Claude, GPT, GLM. Сама по себе модель не видит файлы и не запускает команды — она только отвечает на текст.

### Runtime

Программа, которая даёт модели руки: читает и пишет файлы проекта, запускает команды, хранит историю разговора. Её ещё называют *AI-агентом* или *AI-ассистентом*. AIKit поддерживает три runtime:

- **Claude Code** — от Anthropic: терминал, десктоп-приложение, плагины для IDE;
- **Codex** — от OpenAI: CLI, десктоп-приложение, плагины для IDE;
- **OpenCode** — открытый runtime, работает с разными моделями.

Модель и runtime — разные вещи: GLM — модель, её запускают через любой из этих runtime.

### Сессия и контекст

Сессия — один разговор с runtime. Контекст — всё, что модель «держит в голове» в этой сессии: сообщения, прочитанные файлы, выводы команд. Контекст ограничен по размеру. Поэтому крупные задачи делят между [агентами](#агент): у каждого свой чистый контекст под свою часть работы.

### Промпт

Текст, который получает модель: твоя задача, инструкция агента, правила проекта. Почти всё в AIKit — промпты, разложенные по файлам так, чтобы runtime подставлял их сам.

## Что AIKit ставит в проект

### Правила проекта

Файл с инструкциями, который runtime читает в начале каждой сессии: стек, структура папок, правила кода, запреты, формат коммитов. В Claude Code это `CLAUDE.md`, в Codex и OpenCode — `AGENTS.md`. AIKit собирает его из базовых правил и правил подключённых профилей.

### Агент

Модель с отдельной ролью и своей инструкцией: «ты — архитектор Vue/Nuxt, прочитай проект и выведи план в таком формате». Его ещё называют *сабагентом*. Главный ассистент запускает агента как помощника. Агент работает в своём контексте и возвращает результат.

Файл агента — Markdown с заголовком (frontmatter): `name`, `description`, `tools` (что агенту разрешено), `output_block` (какой блок он выводит) и текст инструкции. Где лежат агенты: `.claude/agents/` в Claude Code, `.codex/agents/` в Codex, `.opencode/agents/` в OpenCode.

Пример: `vue-architect`, `vue-tester`, `security-auditor`.

### Скилл

Готовый сценарий, папка `<name>/SKILL.md`. Внутри — инструкция «как сделать вот это»: какие агенты нужны, в каком порядке, что проверить. Скилл вызывают командой (`/implement-feature` в Claude Code, `$implement-feature` в Codex). Runtime может вызвать его и сам, если задача подходит под `description` скилла — это **автовызов**.

Скиллы с побочными эффектами (`/capture-memory`, `/set-model`) работают только по явному вызову: в Claude Code это поле `disable-model-invocation: true`.

### Slash-команда

Команда вида `/name`. В AIKit это способ вызвать скилл. Раньше в Claude Code были отдельные команды в `.claude/commands/`, теперь их заменили скиллы — при обновлении кита старые команды убираются.

### MCP-сервер

Инструмент для модели по протоколу MCP (Model Context Protocol). Через него модель управляет браузером (Playwright), читает документацию библиотек (Context7), видит макеты (Figma), ошибки продакшена (Sentry). AIKit описывает серверы один раз и пишет их в родной формат runtime: `.mcp.json`, `.codex/config.toml`, `opencode.json`. Секреты передаются только через переменные окружения.

### Хук

Скрипт, который runtime запускает сам на событие: перед записью файла, после правки, в конце ответа. Хук срабатывает всегда, а правило в тексте модель может забыть. Хуки AIKit не дают записать секреты и `.env`, проверяют коммиты и ветки, запускают линтер и тесты профиля — см. [Как это работает](how-it-works.md#хуки-правила-которые-соблюдаются-всегда).

### Настройки и разрешения

`.claude/settings.json` в Claude Code: какие команды ассистент запускает без вопроса (`Bash(npx vitest *)`), какие файлы ему нельзя читать (`.env`), без соавторства в коммитах. Хранится в git, общий для команды.

### PRODUCT.md

Описание продукта в корне проекта: что за продукт, для кого, ключевые сущности и сценарии. Агенты читают его, чтобы решения учитывали продукт, а не только код. AIKit создаёт шаблон, заполняет его команда.

### Память проекта

Папка `.aikit/memory/`: решения, паттерны и коррекции агентов, накопленные командой. Хранится в git и общая для всех людей и агентов в любом runtime. Её пишет `/capture-memory` после задачи, `/memory-status` показывает, что накоплено.

Это не то же самое, что встроенная память runtime. Например, auto memory Claude Code (`~/.claude/projects/<project>/memory/`) личная: её пишет сам Claude по твоим поправкам, и она есть только на твоей машине. Правило «так делаем в проекте» — в `.aikit/memory/`, «так люблю я» — во встроенную память или `CLAUDE.local.md`. История задач в память не пишется: она уже есть в git и PR.

## Как устроен кит

### Base

Ядро кита — папка `base/`: общие правила, агенты и скиллы, которые ставятся в любой проект: `/implement-feature`, `/security-check`, `/analyze-mvp`, `git-commit`, память. Ядро ничего не знает о конкретных стеках — всё стековое оно берёт из [контракта профиля](#контракт-профиля).

### Профиль

Всё, что нужно для одного стека: папка `profiles/<name>/`. В ней правила стека (`CLAUDE.md`), четыре агента по ролям, специалисты, скиллы стека (`/new-page`, `/new-component`), MCP-серверы, разрешения на команды и [контракт](#контракт-профиля). Сейчас есть `vue-nuxt`. Новый стек добавляется [по шаблону](adding-a-stack.md).

### Контракт профиля

Файл `profiles/<name>/profile.manifest.json` — договорённость между профилем и ядром. Профиль обещает: «у меня есть архитектор, кодер, тестировщик и ревьюер с такими именами, тесты запускаются такой командой, мои файлы лежат там-то». Ядро обещает работать с любым профилем одинаково. Поэтому `/implement-feature` один на все стеки. Поля контракта:

| Поле | Что значит |
|---|---|
| `role` | За какую часть системы отвечает профиль: `web`, `backend` или своя (`mobile`, `mod`) |
| `stack` | Стек словами: «Vue 3, Nuxt 3, Pinia» |
| `agents` | Агенты по [ролям](#роли-агентов) |
| `specialists` | [Специалисты](#специалист) и когда их звать |
| `pipelines` | [Пайплайны](#пайплайн) — цепочки, кроме кода |
| `commands` | [Команды проекта](#команды-профиля): `lint`, `format`, `test`, `build`, `run` |
| `root_markers` | Файлы, по которым установщик находит папку профиля: `nuxt.config.ts`, `manage.py` |
| `path_signals` | Пути, по которым задача относится к профилю: `pages/`, `routers/` |

Полный разбор — в разделе [Как добавить стек](adding-a-stack.md#что-такое-контракт-профиля).

### Роли агентов

Каждый профиль обязан иметь ровно четыре роли — это цепочка кода:

| Роль | Что делает | Выводит |
|---|---|---|
| `architect` | Читает проект, проектирует минимальный набор изменений | `ARCHITECT_PLAN` |
| `coder` | Реализует план | `CODER_RESULT` |
| `tester` | Пишет тесты на сделанное | `TESTER_RESULT` |
| `reviewer` | Проверяет код по правилам стека | `REVIEW_RESULT` |

### Выходной блок

Текст в оговорённом формате, которым агент передаёт работу следующему: `=== ARCHITECT_PLAN === … === END PLAN ===`. Кодер получает план архитектора, тестировщик и ревьюер — результат кодера. Формат блоков не меняют: по нему агенты понимают друг друга.

### Специалист

Дополнительный агент профиля, который подключается к цепочке кода, когда задача подходит под его условие `when`. Он не заменяет четыре роли, а дополняет их советом. Пример: `vue-design-bridge` — если задача идёт от макета Figma, он сверяет план с UI kit до того, как кодер начнёт писать.

### Пайплайн

Цепочка своих агентов профиля для работы, которая не является кодом: модели и текстуры, документация, локализация. Пайплайн идёт сам, если задача целиком подходит под его `when` и код не нужен. Если фиче нужен и код, пайплайн идёт после архитектора, и его результат получает кодер. Чем он отличается от специалиста — в разделе [Как это работает](how-it-works.md#специалисты-и-пайплайны).

### Команды профиля

Команды `install`, `lint`, `format`, `test`, `build`, `run` из контракта. `/implement-feature` и `/fix-bug` проверяют ими результат, `/check-feature` запускает приложение командой `run`, `install` ставит зависимости в worktree, хуки запускают `format` и `lint` после каждой правки и `test`, когда агент закончил. `{files}` в команде заменяется списком изменённых файлов. В проекте команды можно поменять в `.aikit/profiles.json` — обновление кита правку сохранит.

### Worktree

Ещё одна рабочая папка того же git-репозитория на своей ветке. `/implement-feature --worktree` создаёт её в `.aikit/worktrees/<имя>`, агенты пишут код туда, и твоя рабочая папка не меняется, пока ты не согласишься перенести результат.

### TDD

Разработка через тесты: сначала тест, который описывает нужное поведение и падает, потом код, после которого тест проходит. В AIKit — `/implement-feature --tdd`; `/fix-bug` всегда начинает с теста на баг.

### Пак

Набор агентов и скиллов под задачу, а не под стек: `devops` (Docker, CI). Пак ставится вместе с профилем: `attach.sh vue-nuxt --pack devops`. Пак без списка `compatible_profiles` подходит к любому профилю.

### Пресет

Готовая комбинация профилей и паков с именем: `frontend-team` = `vue-nuxt` + `devops`. Ставится одной командой: `attach.sh --preset frontend-team`. Все пресеты — в [каталоге](../site/catalog.html#presets).

### Мульти-профиль

Несколько профилей в одном проекте: `vue-nuxt+java-spring`. Так работает fullstack-проект — фронтенд и бэкенд. Имена агентов и скиллов уникальны во всём ките, поэтому любые профили ставятся вместе без конфликтов.

### Root профиля

Папка профиля в проекте. В монорепо фронтенд может лежать в `web/`, а бэкенд — в `api/`. Установщик ищет папку по `root_markers` (`web/nuxt.config.ts` → `web`) и записывает её в `root` в `.aikit/profiles.json`. Команды профиля запускаются в этой папке.

### .aikit/profiles.json

Файл в проекте, где собраны контракты всех подключённых профилей плюс найденный `root`. Его читают `/implement-feature` и агенты в любом runtime. `commands` и `root` в нём можно править под проект. Рядом лежит `.aikit/profiles.kit-defaults.json`: в нём прежние значения кита, по ним обновление понимает, что именно поменяла команда.

### Адаптер

Часть кита, которая раскладывает одни и те же агенты, скиллы и правила в формат конкретного runtime. Для Claude Code это `attach.sh`, для Codex и OpenCode — `install-adapter-package.py`. Описания адаптеров лежат в `adapters/<runtime>/`.

### Установщик

Скрипт, который подключает кит к проекту: `scripts/attach.sh` (Claude Code) или `scripts/install-adapter-package.py` (Codex, OpenCode). Обновляют установку `update.sh` и `update-adapter-package.py`.

### Плагин

Пакет агентов, скиллов, хуков и MCP-серверов, который runtime ставит из маркетплейса и обновляет сам. Маркетплейс AIKit называется `aikit` и лежит в этом репозитории: ядро — плагин `aikit`, каждый профиль и пак — свой плагин. Проект после установки подключает скилл `/aikit:setup`. Работает в Claude Code и Codex; плагины Codex не умеют поставлять агентов, их `/aikit:setup` пишет в `.codex/agents/`.

### .aikit-config

Папка, куда кит подключается к проекту как git submodule — ссылка на репозиторий AIKit внутри твоего репозитория. Все скрипты запускаются оттуда: `bash .aikit-config/scripts/attach.sh`.

### Оркестратор

Скилл или агент, который сам не пишет код, а ведёт цепочку других агентов: `/implement-feature`, `/fix-bug`, `tech-planner`.
