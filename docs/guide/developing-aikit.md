# Разработка AIKit

Как устроен репозиторий кита, какие правила держат его в порядке и как проверить изменения. Страница для тех, кто развивает сам AIKit, — людей и AI-агентов. Перед изменением кита прочитай её целиком.

## Принципы

1. **Источник один.** Агенты, скиллы, правила и MCP-серверы описываются один раз — в `base/`, `profiles/`, `packs/`. В формат каждого runtime их раскладывают установщики и генератор плагинов. Файлы под конкретный runtime руками не пишут.
2. **Ядро не знает стеков.** Базовые скиллы и оркестраторы не называют агентов профилей и стековые команды. Всё стековое они берут из `.aikit/profiles.json`, а он собирается из контрактов. Это проверяет статическая проверка.
3. **Каждая задача — для всех runtime.** Задача закрыта, когда сделана для Claude Code и Codex. Для OpenCode она сделана или явно отмечена как невозможная в [docs/runtime-support.md](../runtime-support.md).
4. **Имена уникальны во всём ките.** Нет двух агентов или двух скиллов с одним именем — поэтому любые профили и паки ставятся вместе без переименований.
5. **Минимальный diff.** Попутно не рефакторить. Одна задача — один коммит.

## Как добавить…

### Агента

Файл `<слой>/agents/<name>.md`, где слой — `base`, `profiles/<p>` или `packs/<p>`. Frontmatter: `name` (совпадает с именем файла), `description` (что делает и когда звать), `tools`, `model` — уровень (`opus` для решений, где ошибка дороже всего: архитектура, ревью, безопасность; `haiku` для простых частых задач; иначе `sonnet`), при необходимости `output_block`, `example_prompt`. Можно начать с `/create-agent`. Агент профиля в одной из четырёх ролей прописывается в `agents` контракта, специалист — в `specialists`, шаг пайплайна — в `pipelines`.

### Скилл

Папка `<слой>/skills/<name>/SKILL.md`. `description` пиши под автовызов: что делает и «Используй, когда…». Скилл с побочными эффектами помечай `disable-model-invocation: true`. Можно начать с `/create-skill`. Новый скилл ядра добавь в [Команды](commands.md) — иначе проверка документации упадёт.

### Профиль

`python3 scripts/new-profile.py …` и дальше по [Как добавить стек](adding-a-stack.md).

### Пак

Папка `packs/<name>/` с `pack.json`: `name`, `label`, `description`, `agents`, `skills` и, если пак подходит не ко всем стекам, `compatible_profiles`. Затем `python3 scripts/build-plugins.py` — пак станет плагином маркетплейса.

### Пресет

`presets/<name>.json`: `name`, `label`, `description`, `profiles`, `packs`. Smoke-тесты CI сами прогоняют каждый пресет.

### Хук

Логика всех хуков — в `base/hooks/aikit_hook.py`: один обработчик на событие (`PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`), вход — JSON в формате Claude Code и Codex. Плагин `base/hooks/opencode-plugin.js` переводит события OpenCode в тот же формат. Новое событие — запись в `EVENTS` в `scripts/hooks_config.py` и обработчик в скрипте. Скрипт без зависимостей, Python 3.9+. Каждое правило — сценарий в `scripts/ci/test-hooks.py`.

### Панель AIKit Deck

Мод Claude Code в плагине ядра: `deck/register.js` — события и отрисовка, `deck/catalog.js` — чистые функции (каталог из `SKILL.md`, разбор `argument-hint`, субагенты, память). Группы базовых команд — `GROUPS` в `catalog.js`; новый базовый скилл без группы попадает в «Прочее». Команды профилей и паков панель берёт из их `skills/` сама. API модов — [документация Claude Code](https://code.claude.com/docs/en/plugins/mods/overview).

Панель не должна вызывать модель: `claude plugin validate .` печатает все её вызовы API (`calls:`) — `$.model` среди них быть не должно. Тесты — `claude plugin test` в корне репозитория, без сессии и сети; в CI Claude Code нет, поэтому их запускает только `run-all.sh`. Вживую: `claude --plugin-dir .` в проекте с `.aikit/profiles.json`, затем `/deck`.

### Модели агентов

Агент называет уровень, а не модель: `model: opus | sonnet | haiku`. Какая модель стоит за уровнем в каждом runtime, задаёт `adapters/models.json`: в Claude Code — алиасы (всегда последняя версия семейства), в Codex — `model` и `model_reasoning_effort` в TOML агента, в OpenCode — `model` в формате `provider/model`. Установщики применяют его через `scripts/agent_models.py`, вместе с переопределениями проекта из `.aikit/models.json` (их пишет `/set-model`). Модели Codex и OpenCode устаревают — раз в несколько месяцев запускай `/check-models` в репозитории кита: он сверит `adapters/models.json` с официальной документацией и предложит правки. Скилл ищет в интернете и тратит лимиты, поэтому только ручной.

### MCP-сервер

`mcp.json` слоя в формате `{"servers": {...}}`. Версию пакета закрепляй (`@1.2.3`, не `@latest`). Секреты — только переменные окружения: `${VAR}`. После правки пересобери плагины: `python3 scripts/build-plugins.py`.

## Плагины и разработка на самом себе

- Маркетплейс и манифесты плагинов генерируются из источников: поменял агентов, скиллы, MCP, хуки или добавил профиль — запусти `python3 scripts/build-plugins.py` и закоммить результат. Статическая проверка сравнивает манифесты с источниками.
- Агенты, скиллы и хуки кита в этом репозитории не копируются в `.claude/` — их дают плагины прямо из рабочей копии. Для разработки запускай Claude Code с плагином ядра:

  ```bash
  claude --plugin-dir .
  ```

  Изменения в `base/` подхватываются после перезапуска сессии. Профиль или пак добавляются ещё одним флагом: `--plugin-dir profiles/vue-nuxt`.
- Проверить установку так, как её видит пользователь, — локальный маркетплейс: `/plugin marketplace add ./` и `/plugin install aikit@aikit`.
- `claude plugin validate .` проверяет маркетплейс и манифесты по схеме Claude Code. Предупреждения про `CLAUDE.md` в корне плагина и отсутствие `version` ожидаемы: версия не задана намеренно, чтобы плагины обновлялись с каждым коммитом в `main`.

## Эвалы

Эвалы — регрессионные тесты поведения агентов и скиллов: эталонные задачи прогоняются через настоящую модель, результат оценивается автоматически. Проверки CI ловят сломанные файлы, эвалы — агентов, которые стали работать хуже после правки промпта, описания скилла или выхода новой модели.

Каждый прогон — настоящие вызовы модели: на подписке они тратят её лимиты (пятичасовое окно и недельный), при входе по API-ключу — оплачиваются. Поэтому эвалы не запускаются ни в CI, ни хуками. Запускай их сам, когда менял агентов, скиллы или хуки.

Эвалы разбиты на группы: `core` — ядро (скиллы `base/`, хуки), и по группе на профиль. Поменял один профиль — гоняй только его группу, остальные не тратят ни времени, ни денег:

```bash
python3 scripts/run-evals.py vue-nuxt --quick             # один профиль, каждый кейс один раз
python3 scripts/run-evals.py vue-nuxt core                # несколько групп, полный прогон
python3 scripts/run-evals.py --changed --quick            # группы, которые задели изменения ветки и незакоммиченные правки
python3 scripts/run-evals.py all --quick                  # все группы (то же без аргументов)
python3 scripts/run-evals.py vue-nuxt --runtime both --quick   # Claude Code и Codex рядом
python3 scripts/run-evals.py vue-nuxt --list              # состав и объём, без прогона
```

`--changed` сравнивает ветку с `origin/main` (другая база — `--changed <ветка>`): правка `profiles/<профиль>/`, его кейсов или фикстуры — только эта группа; правка `base/`, `evals/lib/`, адаптеров или подключения проекта (`plugin-init.py`, `profile_contract.py`, `hooks_config.py`, установщик) — все группы, потому что от них зависит каждый кейс. Паки и документация эвалов не затрагивают. Опечатка в имени группы — ошибка со списком групп, а не прогон всего набора.

Удобнее — скиллом: `/run-evals vue-nuxt`, `/run-evals changed`, `/run-evals all` в Claude Code (`$run-evals` в Codex). Без аргумента скилл предложит группы, затронутые изменениями, конкретный профиль или все, покажет состав и объём и спросит перед запуском. Сам по себе скилл не срабатывает.

| Режим | Что запускается | Объём по прайсу API (sonnet, судья haiku) |
|---|---|---|
| `--quick` | кейс × 1 прогон | ≈ $0.07 на кейс: профиль ≈ $0.15, все группы ≈ $0.7 |
| по умолчанию | кейс × 3 прогона × 2 (с плагином и без) | ≈ $0.4 на кейс: профиль ≈ $0.85, все группы ≈ $4 |

Доллары — это оценка `claude plugin eval` по прайсу API: сколько стоили бы те же токены при оплате по ключу. На подписке деньги не списываются, оценка нужна, чтобы сравнивать прогоны: полный тратит примерно в 6 раз больше `--quick`, один профиль — примерно в 5 раз меньше всех групп. Оценку для выбранных групп печатает `--list`.

Сколько прогон съел из лимитов подписки, раннер показывает в конце: до прогона и после он делает по одному короткому запросу `claude -p` и печатает занятость окон, например «5 часов 20% → 27% (+7), неделя 31% → 32% (+1)». Это занятость всего аккаунта — другие сессии, идущие в это время, тоже в ней; изменения меньше 1% не видно. Замер — в `evals/results/<время>/claude/limits.json`, отключить — `--no-limits`. Лимиты Codex (ChatGPT) раннер не замеряет.

Потолок по умолчанию — `--max-cost-usd 10`: когда оценка по прайсу доходит до него, новые прогоны не стартуют. На подписке это предохранитель от того, чтобы прогон не съел большую часть лимита.

### Как устроено

- Кейс — папка `evals/<группа>/<кейс>/`: `prompt.md` (запрос, как его написал бы человек, лимиты ходов и инструменты), `graders/*.md` (оценщики), `case.yaml` и `setup.sh`, если нужен проект. Группа — `core` или имя профиля, она же тег в `tags`, по которому раннер выбирает кейсы.
- `setup.sh` вызывает `evals/lib/setup-project.sh <профили> <фикстура>`: копирует проект из `evals/fixtures/` и подключает кит — `plugin-init.py` для Claude Code, установщик адаптера для Codex. Команды профиля из `.aikit/profiles.json` убираются: в фикстурах нет `node_modules` и окружения Python, и результат не должен зависеть от того, что стоит на машине.
- Claude Code: `claude plugin eval` в изолированной сессии грузит плагин ядра и плагин профиля (`plugins:` в `prompt.md`). `CLAUDE.md` проекта и личные настройки в прогон **не попадают** — эвалы мерят то, что дают сами плагины. Режим по умолчанию повторяет каждый кейс без плагина: `Δ` показывает, что добавил кит.
- Codex своей команды для эвалов не имеет: раннер готовит тот же проект, запускает `codex exec` и считает оценщики, не зависящие от Claude Code, — регулярки по ответу, трассе или файлу и `file_exists`. `tool_used` (вызван ли скилл или агент) и судья-модель в Codex пропускаются, поэтому `--runtime both` сравнивает только общие проверки. Codex запускает хуки проекта только после одобрения в `/hooks`, поэтому в `codex exec` кейс `env-file-blocked` может провалиться не по вине кита. Путь Codex проверен на подставном `codex`, вживую ещё не прогонялся.
- Bash в кейсах не разрешён: на Windows у Claude Code нет песочницы для команд, и такие прогоны отклоняются. Кейсы обходятся `Read`, `Write`, `Edit`, `Skill` и `Agent`.
- На Windows `python3` часто — лаунчер Python Install Manager. Во временном домашнем каталоге прогона он не находит Python, и хуки плагина падают. Раннер кладёт первым в `PATH` свой `python3`, который указывает прямо на интерпретатор. Без раннера, голым `claude plugin eval`, хук-кейсы на такой машине провалятся.
- Результаты — `evals/results/<время>/` (в `.gitignore`): `claude/report.html` и `aggregate-result.json`, `codex.json`.

### Оценщики

| Тип | Когда брать |
|---|---|
| `regex` по ответу (`target` по умолчанию) или по файлу (`target: { source: file, path: … }`) | Основной: без вызовов модели и стабильный. Ревью — «нашёл ли заложенную ошибку», генерация — «есть ли в файле нужный паттерн» |
| `file_exists` (`exists: false` — файла быть не должно) | Создан ли файл: слой сервисов, запрещённый `.env` |
| `tool_used` с `tool: Skill` или `Agent` | Сработал ли скилл или агент кита. В режиме с базовой линией это индикатор, в оценку не входит |
| `llm` | Только для короткого ответа, который регуляркой не проверить: каждый оценщик — ещё три вызова модели-судьи, и вердикт шумный |

### Новый кейс

1. Папка `evals/<группа>/<кейс>/`, в `prompt.md` — `tags: [<группа>]`, у кейса профиля `plugins: ["../../..", "../../../profiles/<профиль>"]`. Кейс только для Claude Code — тег `claude-only`. У нового профиля заведи группу `evals/<профиль>/`, иначе `run-evals.py <профиль>` скажет, что кейсов нет.
2. Нужен проект — `case.yaml` с `scaffold_script: setup.sh` и `setup.sh` по образцу соседнего кейса. Фикстура — маленький проект в `evals/fixtures/`, ошибки для ревью закладывай явно.
3. Промпт формулируй как пользователь и давай все детали: скиллы профиля просят уточнения, а в прогоне отвечать некому.
4. `python3 scripts/run-evals.py --check`, затем `python3 scripts/run-evals.py --case <кейс> --quick`.

  ```bash
  python3 scripts/generate-docs.py
  ```

- После слияния в `main` workflow `.github/workflows/pages.yml` публикует `docs/site/` на GitHub Pages: https://undef1ned-dev.github.io/ai-kit/.
- Ссылки на файлы вне сайта (исходники агентов, скриптов) генератор ведёт на GitHub, в ветку `main`.
- Порядок страниц и меню задаёт список `PAGES` в `scripts/generate-docs.py`. Новая страница — новая запись в нём.
- Страница «Каталог профилей» строится из `base/`, `profiles/`, `packs/` и `presets/`. Новый агент или скилл появится в каталоге сам — нужно только пересобрать сайт.
- Ссылки между страницами пиши на `.md`-файлы (`[Термины](glossary.md#агент)`): на GitHub они работают как есть, на сайте генератор заменит их на `.html`. Битая ссылка или якорь — ошибка проверки.
- Компоненты сайта, которые на GitHub выглядят обычным Markdown:
  - `<!-- cards -->` перед списком `[Заголовок](ссылка) — текст` — сетка карточек;
  - `<!-- chain -->` перед списком `**имя** — текст` — схема со стрелками;
  - `<!-- steps -->` перед нумерованным списком — шаги;
  - `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]` — выделенные блоки.
- Изменил поведение кита — обнови документацию в том же PR: страницу, которой это касается, [Известные ошибки](known-issues.md), строку в [roadmap](../roadmap.md) и матрицу [runtime](../runtime-support.md).

## Проверки

Все проверки CI одной командой, локально:

```bash
bash scripts/ci/run-all.sh
```

Запускай её перед каждым коммитом, который меняет скрипты, агентов, скиллы или контракты. Минуты CI ограничены, поэтому лучше поймать ошибку локально.

| Проверка | Что ловит |
|---|---|
| `scripts/ci/static-checks.sh` | Синтаксис `*.sh`, `*.py`, `*.json`; каталог видит все скиллы; контракты профилей полные и ссылаются на существующих агентов (роли, специалисты, пайплайны); ядро не называет агентов профилей; имена агентов и скиллов уникальны; сайт документации собран из актуальных исходников и без битых ссылок; манифесты плагинов актуальны; сценарии хуков (`scripts/ci/test-hooks.py`); кейсы эвалов и раннер на подставном `codex` (`scripts/ci/test-run-evals.py`); модели агентов (`scripts/ci/test-agent-models.py`); мод AIKit Deck: модуль на месте, группы ссылаются на существующие скиллы, синтаксис JS |
| `scripts/ci/smoke-attach.sh <preset>` | `attach.sh` и `update.sh --auto` на пустом проекте, хуки подключены и не задваиваются |
| `scripts/ci/smoke-adapter.sh <codex\|opencode> <preset>` | Установка и обновление адаптера; файлы, которые реально читает runtime, хуки |
| `scripts/ci/smoke-plugin.sh <preset>` | Подключение проекта к плагинам (`plugin-init.py`) для Claude Code и Codex: блок правил один и сохраняет текст команды, настройки и плагины, агенты Codex, смена профилей |
| `scripts/ci/smoke-new-profile.sh` | Профиль из шаблона ставится без правок ядра, вместе с пайплайном, в монорепо |
| `claude plugin test` | Мод AIKit Deck: кнопки, поле аргумента, режимы, справка, субагенты, память. Только локально, если установлен Claude Code |

CI (`.github/workflows/ci.yml`) запускает то же самое на Linux и Windows.

### Windows

- Нужна команда `python3` — см. [Известные ошибки](known-issues.md#windows-нет-команды-python3).
- Вывод скриптов с кириллицей: `export PYTHONIOENCODING=utf-8`.
- Скрипты пишут файлы с переводом строки `\n`. Не сохраняй `.sh` с CRLF — bash на них падает.

## Git

- Ветки — по Conventional Branch: `feat/…`, `fix/…`, `docs/…`, `chore/…` (скилл `git-branch`).
- Коммиты — по Conventional Commits, описание на русском: `feat(profiles): …` (скилл `git-commit`).
- Без `Co-Authored-By` и приписок «Generated with» — ни в коммитах, ни в описаниях PR.
- Один этап roadmap — один PR в `main`.

## Порядок работы над задачей

<!-- steps -->
1. Найди задачу в [roadmap](../roadmap.md) и прочитай связанные разделы этой документации.
2. Создай ветку от свежего `main`.
3. Сделай изменение в источниках (`base/`, `profiles/`, `packs/`, `scripts/`), не в копиях.
4. Обнови документацию: Markdown и `python3 scripts/generate-docs.py`.
5. Отметь задачу в roadmap и обнови матрицу runtime, если что-то поменялось для какого-то runtime.
6. `bash scripts/ci/run-all.sh` — всё зелёное.
7. Коммит, PR с описанием «что сделано и зачем».
