Разработка AIKit

Как устроен репозиторий кита, какие правила держат его в порядке и как проверить изменения. Страница для тех, кто развивает сам AIKit, — людей и AI-агентов. Перед изменением кита прочитай её целиком.

#Принципы

  1. Общие требования и самостоятельные инструкции runtime. Общие правила — в base/RULES.md и profiles/<name>/RULES.md; инструкции runtime — в adapters/<runtime>/rules.md. Их собирает scripts/rules.py без перевода текста Claude в Codex. Агенты и скиллы Codex имеют самостоятельные источники в <слой>/codex/; хуки имеют отдельную оболочку Codex, разрешения — нативный профиль с явным выбором.
  2. Ядро не знает стеков. Базовые скиллы и оркестраторы не называют агентов профилей и стековые команды. Всё стековое они берут из .aikit/profiles.json, а он собирается из контрактов. Это проверяет статическая проверка.
  3. Каждая задача — для всех runtime. Задача закрыта, когда сделана для Claude Code и Codex. Для OpenCode она сделана или явно отмечена как невозможная в docs/runtime-support.md.
  4. Имена уникальны во всём ките. Нет двух агентов или двух скиллов с одним именем — поэтому любые профили и паки ставятся вместе без переименований.
  5. Минимальный diff. Попутно не рефакторить. Одна задача — один коммит.
  6. Кит не вызывает модель сам. Ни CI, ни хуки, ни cron, ни AIKit Deck не запускают модель и не тратят лимиты. Эвалы и /check-models — только по явной команде человека.

#Как добавить…

#Агента

Файл <слой>/agents/<name>.md, где слой — base, profiles/<p> или packs/<p>. Frontmatter: name (совпадает с именем файла), description (что делает и когда звать), tools, model — уровень (opus для решений, где ошибка дороже всего: архитектура, ревью, безопасность; haiku для простых частых задач; иначе sonnet), effort — уровень усилий в Claude Code (high у архитекторов *-architect, у остальных medium), при необходимости output_block, example_prompt. Можно начать с /create-agent. Агент профиля в одной из четырёх ролей прописывается в agents контракта, специалист — в specialists, шаг пайплайна — в pipelines.

Агенты профиля работают сабагентами /implement-feature и /fix-bug, поэтому не спрашивают пользователя по ходу работы («использовать Context7?», «передать дальше?») и не запускают следующего агента: вопросы — в поле QUESTIONS блока, передачу ведёт оркестратор. MCP вроде Context7 агент использует сам, когда нужно, а если сервер недоступен — пропускает. Блок закрывается маркером с тем же именем: === ARCHITECT_PLAN === … === END ARCHITECT_PLAN ===. Ревьюер работает параллельно с тестировщиком и TESTER_RESULT не получает — не ставь ревьюеру depends_on на тестировщика.

Для Codex отдельно создай <слой>/codex/agents/<name>.toml: name, description, developer_instructions, реальный model и model_reasoning_effort. Модель по умолчанию не выводится из уровня Claude; уровни остаются совместимыми переопределениями проекта. Заполни <слой>/codex/catalog.json (output_block, context_blocks, depends_on, example_prompt). test-codex-content.py проверяет полноту нативного набора и независимость сборки.

#Скилл

Папка <слой>/skills/<name>/SKILL.md. description пиши под автовызов: что делает и «Используй, когда…». Скилл с побочными эффектами помечай disable-model-invocation: true и клади рядом agents/openai.yaml с policy.allow_implicit_invocation: false — тот же запрет для Codex: плагин и адаптер Codex читают его из папки скилла, расхождение ловит статическая проверка. Можно начать с /create-skill. Новый скилл ядра добавь в Команды — иначе проверка документации упадёт.

Скилл, который спрашивает пользователя по ходу работы (интервью, выбор вариантов, согласие на удаление, способ сохранения в git), ведёт диалог сам, в основном потоке: сабагент спросить пользователя не может и историю разговора не видит. Агенту такой скилл отдаёт уже собранные ответы и нужный контекст разговора; не хватает данных — агент возвращает QUESTIONS, скилл спрашивает и запускает его снова, не больше одного лишнего круга. Так устроены /create-agent, /create-skill, /analyze-mvp, /implement-mvp, /capture-memory и /optimize-memory.

Установщик OpenCode заменяет в текстах агентов и скиллов .claude/agents/ и .claude/skills/ на пути своего runtime. Если текст должен назвать именно папку Claude Code рядом с папками других runtime (как билдеры агентов и скиллов), пиши так, чтобы подстрока не совпала: «agents/<имя>.md в .claude/». В агентах OpenCode CLAUDE.md заменяется на AGENTS.md — кроме строк, где уже есть AGENTS.md, и путей вида profiles/<профиль>/RULES.md: так называй файл кита, а не правила проекта. Codex: плагин читает <слой>/codex/skills/ и base/codex/plugin-skills/; адаптер копирует те же навыки без замены текста. Агенты из <слой>/codex/agents/*.toml копируются в .codex/agents/, затем применяются переопределения проекта. Нет нативного источника — ошибка, отката к Markdown другого runtime нет. Метаданные выходных блоков, зависимостей и примеров — <слой>/codex/catalog.json, в проекте .aikit/agent-catalog.json. Адаптер хранит нативные defaults в .aikit/agents/*.toml.

Для Codex создай независимую папку <слой>/codex/skills/<name>/ и её agents/openai.yaml при явном вызове. Frontmatter — name, description; задача и флаги — из сообщения. Не копируй в сценарий параметры инструментов другого runtime. Роли — локальные TOML, команды — контракт профиля; параллельные агенты запускаются до ожидания. Если роль передана обычному субагенту как текст, нельзя обещать применение модели TOML. Недоступное делегирование останавливает цепочку с объяснением. Живые эвалы запускает только человек.

#Профиль

python3 scripts/new-profile.py … и дальше по Как добавить стек.

#Пак

Папка packs/<name>/ с pack.json: name, label, description, agents, skills и, если пак подходит не ко всем стекам, compatible_profiles. Затем python3 scripts/build-plugins.py — пак станет плагином маркетплейса.

#Пресет

presets/<name>.json: name, label, description, profiles, packs. Smoke-тесты CI сами прогоняют каждый пресет.

#Хук

Логика всех хуков — в base/hooks/aikit_hook.py: один обработчик на событие (PreToolUse, PostToolUse, Stop, SessionStart), вход — JSON в формате Claude Code и Codex. Плагин base/hooks/opencode-plugin.js переводит события OpenCode в тот же формат. Новое событие — запись в EVENTS в scripts/hooks_config.py и обработчик в скрипте. Скрипт без зависимостей, Python 3.9+. Каждое правило — сценарий в scripts/ci/test-hooks.py.

Хук не ходит в сеть на старте сессии. Уведомление о новой версии (только --plugin) читает кэш, а раз в сутки запускает себя отсоединённым процессом с --refresh-update-cache — тот забирает VERSION из main. В тестах адрес и кэш подменяются переменными AIKIT_UPDATE_URL (подходит file://) и AIKIT_UPDATE_CACHE.

Команды хуков Codex для Windows (commandWindows в hooks_config.py и build-plugins.py) — без синтаксиса shell. Codex запускает их через powershell -NoProfile -Command (shell сессии) или cmd.exe /C: ${VAR} и $(...) там не работают, переменные плагина (PLUGIN_ROOT) приходят только через окружение, а Windows PowerShell 5.1 превращает код выхода 2 в 1. Поэтому команда — лаунчер python -c, а блокирует хук JSON-ответом (--deny-json). Нативная оболочка base/codex/hooks/aikit_hook.py задаёт runtime явно, игнорирует CLAUDE_PROJECT_DIR и формирует JSON-отказ на всех ОС; общий движок правил остаётся в base/hooks. test-hooks.py прогоняет обе команды из подпапки проекта в cmd.exe и PowerShell (на Linux — в sh).

Лаунчер строит hooks_config.windows_launcher: его программа (Python 2 и 3 разбирают её одинаково) — base64, чтобы в строке команды не было кавычек. Если python старее 3.9, он находит py -3 или python3 версии 3.9+ и передаёт им событие. Не нашёл — пропускает действие и оставляет launch-error.txt во временной папке.

Каждый запуск хука оставляет отметку run-*.json (событие, время, интерпретатор, последняя внутренняя ошибка — без содержимого событий и файлов); aikit_hook.py --status печатает по ним состояние ok, no-mark, internal-error или launcher-error, его читает /aikit:setup. Тесты подменяют временную папку на свою.

Живая проверка хуков Codex (вручную, на Windows). Хуки в настоящей сессии Codex в CI не прогоняются: это модельные запросы, а они запускаются только вручную. Перед релизом, который трогает хуки, пройди на тестовом проекте с искусственными данными (без секретов), без --dangerously-bypass-hook-trust:

  1. Установи плагин (и отдельно адаптер), одобри хуки в /hooks, перезапусти сессию. aikit_hook.py --status — ok после первого ответа; python --version вне хука не считается проверкой.
  2. Проверь из корня проекта и из подпапки с пробелом: в .aikit/memory/INDEX.md и PRODUCT.md лежат метки — агент называет их, не читая файлы.
  3. Попроси записать .env: через apply_patch, перенаправлением (echo A=1 > .env) и Set-Content. Все три блокирует AIKit (в ответе его сообщение); запись .env.example и обычного файла проходит. Отказ песочницы Windows (Failed to write file) не засчитывается как блокировка.
  4. Подставь в профиль заглушки format, lint, test, пишущие в журнал: после правки файла в журнале format → lint, ошибка линтера доходит до агента, при test с кодом 1 завершение блокируется, при коде 0 — нет.
  5. Полный цикл в одной сессии: падающие тесты → блокировка Stop → агент исправляет → тесты проходят → сессия завершается.
  6. Сохрани версию Codex, статус хуков из /hooks, фактический результат каждого шага; перегрузку модели отмечай отдельно, она не считается ошибкой хуков.

#Панель AIKit Deck

Мод Claude Code в плагине ядра: deck/register.js — события и отрисовка, deck/catalog.js — чистые функции (каталог из SKILL.md, разбор argument-hint, субагенты, память). Группы базовых команд — GROUPS в catalog.js; новый базовый скилл без группы попадает в «Прочее». Команды профилей и паков панель берёт из их skills/ сама, свои скиллы проекта — из .claude/skills/ корня проекта; скилл проекта, названный в GROUPS (improve-aikit репозитория кита), встаёт в эту группу, остальные — в «Скиллы проекта». Модель субагента панель берёт из события turn.step (e.agentId, result.usage.model): в документации $.agent.list() поля модели нет (если оно появится в списке, панель возьмёт его первым). Хук turn.step только читает запрос и передаёт его дальше без изменений. Блок «Действия проекта» берёт кнопки из actions профилей в .aikit/profiles.json (источник — actions контракта, scripts/profile_contract.py сохраняет правки команды так же, как commands) и сам добавляет каждому профилю «Обновить профиль» по имени его плагина; программы запускает $.process.spawn по argv, без shell. На Windows .bat и .cmd (gradlew.bat, claude.cmd из npm) без shell не стартуют, поэтому hostArgv в catalog.js запускает там каждое действие через cmd /d /c и отказывается от аргументов с & | < > ^ % ". Claude Code задаёт дочерним процессам NoDefaultCurrentDirectoryInExePath=1, и cmd.exe с ней не ищет программу в текущей папке: cmd /d /c gradlew.bat падает с «не является внутренней или внешней командой». Поэтому программа из папки профиля — argv[0] с ./ или .\ или имя из WINDOWS_SCRIPTS — получает явный путь (./gradlew → .\gradlew.bat), а программа из PATH (claude, git) остаётся как есть: её cmd.exe находит по PATH и PATHEXT. Обработчик кнопки не ждёт процесс (void runAction(...)): runClient живёт, пока открыта игра. Обновления плагинов («Обновить кит», «Обновить профиль») сообщают результат тостом (updateToast в catalog.js) и блок вывода не занимают. Плагин бывает установлен в нескольких scope сразу, а claude plugin update <плагин>@aikit без --scope обновляет одну запись — сессия может грузить другую. Поэтому при нажатии панель читает installed_plugins.json и обновляет каждую запись плагина для проекта (updateRecords: user, а project и local — с projectPath этого проекта; managed и чужие проекты не трогает) шагом claude plugin update <плагин>@aikit --scope <scope> после claude plugin marketplace update aikit; записей нет — один шаг без --scope. Тост сравнивает версию, которую выполняет сессия, с наибольшей версией обновлённых записей, а упавший шаг называет его scope и «обновлён» не пишет. Панель, которую мод открывает сам ($.ui.open в session.start), движок размещает только в окне шире порога (144 колонки, 110 — если человек уже открывал этот id) и при наличии поверхности. Иначе $.ui.open отвечает { isPlaced: false, reason }, и панель ждёт. Открытие по действию человека (его команда, промпт или нажатие кнопки; флаг focus действием не считается) размещается при любой ширине. Поэтому openPane пишет reason в $.ui.log(…, { to: 'debug' }), а пока панель не размещена, хук ui.render AbovePrompt рисует в полосе над полем ввода «AIKit Deck» с кнопкой «Открыть». Строка режимов (SessionMode) для этого не годится: до первого сообщения её может не быть. Полоса держит одно дерево: при e.props.hasSurvey или если next(e) вернул не узел движка { type: 'engine' } (полосу занял другой мод), панель отдаёт next(e). В claude plugin test под модами нет отрисовки движка, поэтому тест сам отвечает на ui.render полосы узлом { type: 'engine', ref: 0 }. Версии в шапке читаются при старте сессии: кита — version из .claude-plugin/plugin.json корня плагина ядра (то, что сессия выполняет), профилей и паков — запись <плагин>@aikit в installed_plugins.json, который лежит рядом с кэшем плагинов (pluginsDir выводит путь из $.plugin.root, без переменных окружения): у плагина бывает несколько записей, запись local или project с projectPath этого проекта сильнее записи user. В claude plugin test корень плагина — рабочая копия, не кэш, поэтому версии профилей в тестах панели не видны: их выбор проверяется тестами чистых функций. В claude plugin test настоящего $.process нет: тест подменяет process.spawn генератором, который отдаёт куски { stream, text } и возвращает { value: { code, signal } } — голый { code, signal } движок теста отвергает. API модов — документация Claude Code.

Панель не должна вызывать модель: claude plugin validate . печатает все её вызовы API (calls:) — $.model среди них быть не должно. Тесты — claude plugin test в корне репозитория, без сессии и сети; в CI Claude Code нет, поэтому их запускает только run-all.sh. Вживую: claude --plugin-dir . в проекте с .aikit/profiles.json, затем /deck.

#Модели агентов

Codex хранит defaults непосредственно в <слой>/codex/agents/*.toml: реальный model и model_reasoning_effort. Плагин и адаптер копируют эти определения, затем agent_models.py применяет ключ codex из .aikit/models.json. Установка не читает Markdown Claude для выбора модели или инструкции. Строковые уровни opus, sonnet, haiku остаются совместимыми переопределениями через adapters/models.json; конкретный id Codex сохраняет нативное усилие роли.

Claude Code использует model и effort во frontmatter Markdown: архитекторы high, остальные medium. Плагины читают исходники, attach.sh копирует их; смена модели не меняет effort. OpenCode пока разрешает уровни из Markdown через adapters/models.json. /check-models проверяет нативные TOML Codex отдельно от карты совместимости и источников других runtime; запускать его можно только по явной просьбе, поскольку он расходует лимиты.

#MCP-сервер

mcp.json слоя в формате {"servers": {...}}. Версию пакета закрепляй (@1.2.3, не @latest). Секреты — только переменные окружения: ${VAR}. После правки пересобери плагины: python3 scripts/build-plugins.py.

Агент с явным списком tools: не получает MCP-инструменты родительской сессии, пока их не перечислить. Если агент вызывает MCP, добавь в tools: сервер целиком в двух видах: mcp__<сервер>__* (установка через attach.sh) и mcp__plugin_<плагин>_<сервер>__* (установка плагинами, плагин — тот, чей mcp.json объявляет сервер: aikit для context7, vue-nuxt для figma). Поле mcpServers во frontmatter у агентов плагина игнорируется. Статическая проверка падает, если в тексте агента есть mcp__<сервер>__, а в tools: его нет.

#Правила проекта и граница runtime

base/RULES.md содержит язык, Git-workflow, качество, безопасность, общие правила работы и каталог скиллов по именам. profiles/<name>/RULES.md добавляет только требования стека. В этих файлах нет команд и путей конкретного AI-runtime.

adapters/codex/rules.md, adapters/claude/rules.md и adapters/opencode/rules.md описывают вызов скиллов, имена агентов, применение моделей и подключение инструментов своего runtime. Правила Codex не читают инструкцию Claude, и наоборот. Сборщик объединяет готовые разделы без замены названий продуктов и путей в тексте.

Все способы установки используют scripts/rules.py: плагин (plugin-init.py), адаптер, attach.sh и update.sh. В плагине и адаптере блок правил одинаков. Старые маркеры блока AIKit сохранены: повторный setup обновляет его на месте, сохраняя текст команды снаружи и файл другого runtime.

При разработке самого кита меняй источники и выполняй:

bash
python3 scripts/rules.py --repository

Codex использует AGENTS.md, скилл .agents/skills/improve-aikit/ и определение .codex/agents/aikit-maintainer.toml; Claude — CLAUDE.md и свои файлы в .claude/. Локальный скилл сопровождения не направляет к инструкции другого runtime.

У сопровождающего Codex явно заданы model = "gpt-6.1-sol" и model_reasoning_effort = "high"; это самостоятельное определение, которое не собирается из агента Claude. Новая сессия Codex загружает его без префикса плагина. Изменения этих настроек проверяются scripts/ci/test-rules.py: TOML должен содержать реальный идентификатор модели и собственные инструкции Codex.

Тот же набор проверок ставит ядро и оба профиля плагином и адаптером во временные проекты: имена агентов совпадают с контрактами без префиксов, ключ codex переопределяет модель независимо от claude, при обновлении применяются новые значения модели и effort. Проверки читают реальные установленные TOML, но не вызывают модель и не подтверждают доступность модели в подписке.

Правила, агенты, модели и скиллы Codex имеют самостоятельные источники. Плагин и адаптер используют одни нативные инструкции; общими остаются требования, контракты и память. Проверка поставки не доказывает выполнение скилла или выбор роли в живой сессии — это подтверждается отдельным прогоном и трассой.

#Настройки и права Codex

base/codex/settings.toml содержит самостоятельный профиль permissions.aikit. runtime_settings.py поставляет его отдельным .codex/aikit-permissions.example.toml, который не загружается автоматически. Изменённый командой шаблон сохраняется; обычная установка не меняет активный config.toml. Прежний управляемый блок мигрируется только если пользователь не выбрал его явно. Выбор default_permissions, sandbox, approval, trust и сеть установщик не меняет. Поэтому наличие профиля не доказывает активную защиту чтения.

Для явного подключения нужно проверить совместимость клиента, перенести определение из шаблона и выбрать default_permissions = "aikit"; сначала нужно проверить действующие слои настроек: legacy sandbox_mode может перекрывать профиль. Профиль запрещает .env и .env.* (включая шаблоны) в workspace roots, глубина сканирования glob — 16. Файлы, созданные после старта процесса, и более глубокие пути требуют отдельной проверки; после изменения настроек нужна новая сессия. Codex doctor показывает template, definition и application отдельно и не объявляет применение подтверждённым только по TOML.

События Claude и Codex определены независимо в hooks_config.py. Плагин Codex вызывает base/codex/hooks/aikit_hook.py, адаптер — .aikit/hooks/codex/aikit_hook.py. Оболочка наследует разрешения сессии и не одобряет хуки за пользователя. При обновлении изменённые хуки снова требуют /hooks; безопасное совместное обновление сохраняет группы пользователя и настройку другого runtime.

#Единое обновление Codex

update-agents --with-plugins запускает scripts/update-codex-plugins.py. Он читает .aikit/plugin-init.json, проверяет установленные и включённые плагины через codex plugin list --marketplace aikit --json, выполняет codex plugin marketplace upgrade aikit --json и перечитывает список. Путь свежего ядра берётся из source.path ответа CLI, а не из прежнего корня скилла или догадки о структуре кэша. Версия каждой выбранной записи и её манифеста должна совпасть с VERSION ядра; понижение версии отклоняется.

Новый plugin-init.py --refresh-agents выполняется в отдельном процессе из свежего источника, во временном проекте с копией состояния и моделей команды. Нужен Python 3.11+ для проверки TOML. Только после успешной проверки записи переносятся в проект. Новое имя, занятое агентом команды вне прежнего списка AIKit, останавливает обновление. Сбой записи откатывает перенесённые файлы, но не глобальное обновление маркетплейса. Пользовательские правила и контракты не обновляются этим режимом.

codex_agents_version в .aikit/plugin-init.json хранит версию источника последней пересборки (её пишут setup, обычная и единая пересборка); codex_plugin_versions — версии выбранных плагинов при последнем едином обновлении. Это версии файлов, а не уже загруженных в текущую сессию определений. Состояние и модели проверяются повторно перед переносом: если пользователь изменил их во время обновления, скрипт останавливается.

Регрессия — scripts/ci/test-update-codex-plugins.py: подставные ответы CLI, реальный генератор агентов и временные проекты. Сеть, пользовательские плагины и модель в тестах не вызываются. Не запускай единое обновление в реальном профиле разработчика для проверки кода; живой прогон — только по явному запросу на обновление плагинов.

#Диагностика Codex

setup --check запускает scripts/codex-doctor.py без изменения настроек. Без этого флага setup сохраняет прежний сценарий, а для готовности Codex использует тот же отчёт. Диагностика поддерживает установку плагинами, адаптером и разработку самого репозитория; Python 3.11+. Её зависимости из стандартной библиотеки и agent_models.py; адаптер поставляет оба скрипта. Импорт не создаёт __pycache__ в проекте.

Проверяются PATH-интерпретатор хука, точная запись доверия в пользовательском config.toml, ожидаемые TOML-агенты и их модели, версия пересборки, включение выбранных плагинов, наличие ожидаемых MCP и требуемых переменных. Запросы CLI ограничены plugin list и mcp list. В отчёт не копируются транспорт, аргументы, окружение, URL и сообщения ошибок хуков. Соединения MCP, доступ к модели, одобрение хуков и загрузка агентов активной сессией не проверяются.

Поле runtimes в отметках base/hooks/aikit_hook.py хранит события, Python и последнюю ошибку отдельно для Codex и Claude. Старые верхние поля оставлены для --status. Диагностика использует только отдельную ветку codex, не принимает устаревшие общие отметки и не считает глобальный launch-error.txt доказательством ошибки конкретного проекта. Отметки старше суток требуют повторной проверки; одобрение текущей версии хуков всегда имеет статус unknown.

Регрессия — scripts/ci/test-codex-doctor.py: сохранность файлов проекта, скрытие секретов, неверные модели и TOML, отсутствующие плагины и контракты, ошибки и давность отметок, разделение runtime. Ответы CLI подставные; внешние сервисы и модель не вызываются. Живую диагностику можно запускать в рабочей копии: она только читает файлы и конфигурацию CLI.

#Плагины и разработка на самом себе

  • Маркетплейс и манифесты плагинов генерируются из источников: поменял агентов, скиллы, MCP, хуки или добавил профиль — запусти python3 scripts/build-plugins.py и закоммить результат. Статическая проверка сравнивает манифесты с источниками.

  • Агенты, скиллы и хуки кита в этом репозитории не копируются в .claude/ — их дают плагины прямо из рабочей копии. Для разработки запускай Claude Code с плагином ядра:

    bash
    claude --plugin-dir .

    Изменения в base/ подхватываются после перезапуска сессии. Профиль или пак добавляются ещё одним флагом: --plugin-dir profiles/vue-nuxt.

  • Проверить установку так, как её видит пользователь, — локальный маркетплейс: /plugin marketplace add ./ и /plugin install aikit@aikit.
  • claude plugin validate . проверяет маркетплейс и манифесты по схеме Claude Code. Предупреждение про CLAUDE.md в корне плагина ожидаемо.
  • В каждом манифесте и записи маркетплейса есть version — копия файла VERSION. Claude Code и Codex обновляют установленный плагин, только когда она меняется, поэтому версия растёт с каждым релизом (см. Версии и релиз). build-plugins.py --check падает, если version в манифесте не равна VERSION.

#Версии и релиз

Версия кита — файл VERSION (semver). Руками её не правят: после слияния в main workflow .github/workflows/version.yml запускает scripts/bump-version.py, и тот без модели, по Conventional Commits, выбирает степень:

Коммиты слиянияВерсия
есть ! после типа (feat!:, refactor(profiles)!:) или футер BREAKING CHANGE:major
есть featminor
остальное: fix, perf, refactor, docs, chore, build, ci, test, style, сообщения не по форматуpatch

Считаются только коммиты, которые меняют то, что приходит в плагинах: base/, profiles/, packs/, presets/, templates/, adapters/, hooks/, deck/, scripts/, манифесты .claude-plugin/ и .codex-plugin/ — кроме scripts/ci/ и deck/tests/ (список — PLUGIN_PATHS в скрипте, тот же — в paths: workflow). Слияние только документации, эвалов или CI версию не меняет: иначе пользователи получали бы уведомление об обновлении без изменений. Merge-коммиты и прошлые релизы пропускаются; диапазон начинается с последнего коммита, который менял VERSION, поэтому упавший запуск догонит следующий.

Дальше workflow пишет VERSION и секцию CHANGELOG.md (feat — Added, несовместимое и прочее — Changed, fix — Fixed; [Unreleased] для ручных заметок не трогается), пересобирает манифесты и сайт и коммитит от github-actions[bot] chore(release): vX.Y.Z — без соавторства. Этот коммит не запускает ни новый bump, ни CI. Модель нигде не вызывается.

Ruleset main требует зелёный CI, поэтому коммит бота попадает в main одним из двух путей:

  • задан секрет RELEASE_DEPLOY_KEY — пуш прямо в main deploy-ключом с правом записи, которому ruleset разрешает обход (bypass list → Deploy keys);
  • секрета нет — ветка release/vX.Y.Z, PR с auto-merge и запуск CI на ней через workflow_dispatch (пуши и PR от GITHUB_TOKEN сами workflow не запускают). Нужна галочка Settings → Actions → «Allow GitHub Actions to create and approve pull requests». Каждый релиз тратит полный прогон CI.

Посмотреть, что посчитает скрипт, не меняя файлов: python3 scripts/bump-version.py. Теги и GitHub Release по-прежнему ставятся вручную (release.yml по тегу v*).

#Эвалы

Эвалы — регрессионные тесты поведения агентов и скиллов: эталонные задачи прогоняются через настоящую модель, результат оценивается автоматически. Проверки CI ловят сломанные файлы, эвалы — агентов, которые стали работать хуже после правки промпта, описания скилла или выхода новой модели.

Каждый прогон — настоящие вызовы модели: на подписке они тратят её лимиты (пятичасовое окно и недельный), при входе по API-ключу — оплачиваются. Поэтому эвалы не запускаются ни в CI, ни хуками. Запускай их сам, когда менял агентов, скиллы или хуки.

Эвалы разбиты на группы: core — ядро (скиллы base/, хуки), и по группе на профиль. Поменял один профиль — гоняй только его группу, остальные не тратят ни времени, ни денег:

bash
python3 scripts/run-evals.py vue-nuxt --quick             # один профиль, каждый кейс один раз
python3 scripts/run-evals.py vue-nuxt core                # несколько групп, полный прогон
python3 scripts/run-evals.py --changed --quick            # группы, которые задели изменения ветки и незакоммиченные правки
python3 scripts/run-evals.py all --quick                  # все группы (то же без аргументов)
python3 scripts/run-evals.py vue-nuxt --runtime both --quick   # Claude Code и Codex рядом
python3 scripts/run-evals.py vue-nuxt --list              # состав и объём, без прогона

--changed сравнивает ветку с origin/main (другая база — --changed <ветка>): правка profiles/<профиль>/, его кейсов или фикстуры — только эта группа; правка base/, evals/lib/, адаптеров или подключения проекта (plugin-init.py, profile_contract.py, hooks_config.py, установщик) — все группы, потому что от них зависит каждый кейс. Паки и документация эвалов не затрагивают. Опечатка в имени группы — ошибка со списком групп, а не прогон всего набора.

Удобнее — скиллом: /run-evals vue-nuxt, /run-evals changed, /run-evals all в Claude Code ($run-evals в Codex). Без аргумента скилл предложит группы, затронутые изменениями, конкретный профиль или все, покажет состав и объём и спросит перед запуском. Сам по себе скилл не срабатывает.

РежимЧто запускаетсяОбъём по прайсу API (sonnet, судья haiku)
--quickкейс × 1 прогон≈ $0.07 на кейс: профиль ≈ $0.15, все группы ≈ $0.7
по умолчаниюкейс × 3 прогона × 2 (с плагином и без)≈ $0.4 на кейс: профиль ≈ $0.85, все группы ≈ $4

Доллары — это оценка claude plugin eval по прайсу API: сколько стоили бы те же токены при оплате по ключу. На подписке деньги не списываются, оценка нужна, чтобы сравнивать прогоны: полный тратит примерно в 6 раз больше --quick, один профиль — примерно в 5 раз меньше всех групп. Оценку для выбранных групп печатает --list.

Сколько прогон съел из лимитов подписки, раннер показывает в конце: до прогона и после он делает по одному короткому запросу claude -p и печатает занятость окон, например «5 часов 20% → 27% (+7), неделя 31% → 32% (+1)». Это занятость всего аккаунта — другие сессии, идущие в это время, тоже в ней; изменения меньше 1% не видно. Замер — в evals/results/<время>/claude/limits.json, отключить — --no-limits. Лимиты Codex (ChatGPT) раннер не замеряет.

Потолок по умолчанию — --max-cost-usd 10: когда оценка по прайсу доходит до него, новые прогоны не стартуют. На подписке это предохранитель от того, чтобы прогон не съел большую часть лимита.

#Как устроено

  • Кейс — папка evals/<группа>/<кейс>/: prompt.md (запрос, как его написал бы человек, лимиты ходов и инструменты), graders/*.md (оценщики), case.yaml и setup.sh, если нужен проект. Группа — core или имя профиля, она же тег в tags, по которому раннер выбирает кейсы.
  • setup.sh вызывает evals/lib/setup-project.sh <профили> <фикстура>: копирует проект из evals/fixtures/ и подключает кит — plugin-init.py для Claude Code, установщик адаптера для Codex. Команды профиля из .aikit/profiles.json убираются: в фикстурах нет node_modules и окружения Python, и результат не должен зависеть от того, что стоит на машине.
  • Claude Code: claude plugin eval в изолированной сессии грузит плагин ядра и плагин профиля (plugins: в prompt.md). CLAUDE.md проекта и личные настройки в прогон не попадают — эвалы мерят то, что дают сами плагины. Режим по умолчанию повторяет каждый кейс без плагина: Δ показывает, что добавил кит.
  • Codex запускается через codex exec. У кейса могут быть независимые prompt.codex.md и graders.codex/; без них сохраняется совместимость существующих кейсов. Раннер проверяет CLI-код, terminal event turn.completed и непустой финальный ответ. Timeout, turn.failed и terminal error дают score 0 независимо от совпадений регулярных выражений; grader_score сохраняется отдельно. Восстановленные transport errors до успешного завершения остаются warnings, не маскируют успешный ответ. Причина из terminal JSON не теряется за посторонним stderr.
  • JSONL каждого Codex прогона сохраняется в results/<run>/traces/. target: commands рассматривает только успешно завершённые command_execution; упоминание команды в agent_message не считается её выполнением. Нулевой вес native-source-read подтверждает чтение SKILL.md, а не запуск скилла или роли. tool_used: Agent остаётся неизвестным без доказанного формата dispatch. При --runtime both сравниваются только одинаковые определения общих оценщиков.
  • Любой живой прогон, включая диагностику одним модельным запросом, требует отдельного явного одобрения пользователя на конкретный запуск. Общее «продолжай» или «сделай всё» его не заменяет. CI использует подставной CLI и моделей не вызывает. Согласие на один прогон не разрешает следующие.
  • Bash в кейсах не разрешён: на Windows у Claude Code нет песочницы для команд, и такие прогоны отклоняются. Кейсы обходятся Read, Write, Edit, Skill и Agent.
  • На Windows python3 часто — лаунчер Python Install Manager. Во временном домашнем каталоге прогона он не находит Python, и хуки плагина падают. Раннер кладёт первым в PATH свой python3, который указывает прямо на интерпретатор. Без раннера, голым claude plugin eval, хук-кейсы на такой машине провалятся.
  • Результаты — evals/results/<время>/ (в .gitignore): claude/report.html и aggregate-result.json, codex.json.

#Новый кейс

  1. Папка evals/<группа>/<кейс>/, в prompt.md — tags: [<группа>], у кейса профиля plugins: ["../../..", "../../../profiles/<профиль>"]. Кейс только для Claude Code — тег claude-only. У нового профиля заведи группу evals/<профиль>/, иначе run-evals.py <профиль> скажет, что кейсов нет.
  2. Нужен проект — case.yaml с scaffold_script: setup.sh и setup.sh по образцу соседнего кейса. Фикстура — маленький проект в evals/fixtures/, ошибки для ревью закладывай явно.
  3. Промпт формулируй как пользователь и давай все детали: скиллы профиля просят уточнения, а в прогоне отвечать некому.
  4. python3 scripts/run-evals.py --check, затем python3 scripts/run-evals.py --case <кейс> --quick.

#Ограниченная живая проверка Codex, 29–30 октября 2026

CLI 0.165.0-alpha.1.2: commit-message прошёл по содержимому ответа. На отдельной Python stdlib фикстуре нативный implement-feature --tdd реально запустил probe-architect, probe-tester, probe-coder и затем tester/reviewer до ожидания любого из них. Имена ролей подтверждены function_call spawn_agent в собственном rollout прогона; публичный JSONL показывал wait, поэтому его одного недостаточно для вывода о dispatch. Начальное падение было ImportError отсутствующей increment. После кода Codex честно сообщил, что test/lint не подтверждены: его shell выбрал Python 2.7, а прямой Python 3.14 был недоступен в песочнице. Обычный запуск четырёх unit-тестов и assertions под Python 3.14 после прогона прошёл. Это проверка ограниченной цепочки, не доказательство всех флагов и полномочий.

Полный цикл обновлённых доверенных хуков в настоящей сессии и повторная живая проверка Claude остаются отдельной проверкой. Claude eval истёк по timeout после предупреждения о токене; минимальный запрос из пустой папки тоже истёк по timeout. Пользователь отложил живую проверку Claude и затем запретил новые эвалы без отдельного одобрения. Новых модельных вызовов для завершения CI не требуется.

#Документация

  • Текст правится только в Markdown: docs/guide/*.md, docs/roadmap.md, docs/runtime-support.md.

  • После правки собери сайт и закоммить docs/site/ вместе с Markdown:

    bash
    python3 scripts/generate-docs.py
  • После слияния в main workflow .github/workflows/pages.yml публикует docs/site/ на GitHub Pages: https://undef1ned-dev.github.io/ai-kit/.
  • Ссылки на файлы вне сайта (исходники агентов, скриптов) генератор ведёт на GitHub, в ветку main.
  • Порядок страниц и меню задаёт список PAGES в scripts/generate-docs.py. Новая страница — новая запись в нём.
  • Страница «Каталог профилей» строится из base/, profiles/, packs/ и presets/. Новый агент или скилл появится в каталоге сам — нужно только пересобрать сайт.
  • Ссылки между страницами пиши на .md-файлы ([Термины](glossary.md#агент)): на GitHub они работают как есть, на сайте генератор заменит их на .html. Битая ссылка или якорь — ошибка проверки.

  • Компоненты сайта, которые на GitHub выглядят обычным Markdown:

    • <!-- cards --> перед списком [Заголовок](ссылка) — текст — сетка карточек;
    • <!-- chain --> перед списком **имя** — текст — схема со стрелками;
    • <!-- steps --> перед нумерованным списком — шаги;
    • > [!NOTE], > [!TIP], > [!IMPORTANT], > [!WARNING] — выделенные блоки.
  • Изменил поведение кита — обнови документацию в том же PR: страницу, которой это касается, Известные ошибки, строку в roadmap и матрицу runtime.

#Проверки

Все проверки CI одной командой, локально:

bash
bash scripts/ci/run-all.sh

Запускай её перед каждым коммитом, который меняет скрипты, агентов, скиллы или контракты. Минуты CI ограничены, поэтому лучше поймать ошибку локально.

CI (.github/workflows/ci.yml) запускает то же самое на Linux и Windows.

Проверка путей пропускает пути с подстановками (<имя>, {имя}, *, ...) и пути проекта пользователя, начинающиеся с точки (.aikit/, .claude/). Если агент пишет в папку проекта, которая называется как папка кита (например docs/mvp/), добавь её в PROJECT_PATHS проверки с комментарием.

#Windows

  • Нужна команда python3 (в Codex на Windows хуки зовут python) — см. Известные ошибки.
  • Вывод скриптов с кириллицей: export PYTHONIOENCODING=utf-8.
  • Скрипты пишут файлы с переводом строки \n. Не сохраняй .sh с CRLF — bash на них падает.
  • Python на Windows по умолчанию пишет CRLF, и smoke-проверки на Linux падают. Пиши файлы через Path.write_bytes(text.encode("utf-8")) или open(..., newline="\n"). .gitattributes приводит файлы к LF при коммите; проверить индекс — git grep -lI --cached $'\r'.

#Git

  • Ветки — по Conventional Branch: feat/…, fix/…, docs/…, chore/… (скилл git-branch).
  • Коммиты — по Conventional Commits, описание на русском: feat(profiles): … (скилл git-commit).
  • Без Co-Authored-By и приписок «Generated with» — ни в коммитах, ни в описаниях PR.
  • Один этап roadmap — один PR в main.

#Порядок работы над задачей

Задачу по киту можно отдать агенту aikit-maintainer: /improve-aikit <что изменить> в Claude Code или скилл improve-aikit в Codex. Он идёт по шагам ниже и прогоняет run-all.sh.

  1. Найди задачу в roadmap и прочитай связанные разделы этой документации.
  2. Создай ветку от свежего main.
  3. Сделай изменение в источниках (base/, profiles/, packs/, scripts/), не в копиях.
  4. Обнови документацию: Markdown и python3 scripts/generate-docs.py.
  5. Отметь задачу в roadmap и обнови матрицу runtime, если что-то поменялось для какого-то runtime.
  6. bash scripts/ci/run-all.sh — всё зелёное.
  7. Коммит, PR с описанием «что сделано и зачем».
