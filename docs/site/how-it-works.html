Как это работает

Что происходит между командой /implement-feature и готовым кодом: откуда runtime берёт агентов, как выбирается профиль и как агенты передают работу друг другу.

#Три слоя

Источникbase/, profiles/, packs/: общие требования, контракты и MCP; самостоятельные агенты и скиллы Codex в codex/ каждого слоя
→
Доставкаплагины маркетплейса aikit (Claude Code, Codex) или установщик attach.sh / install-adapter-package.py раскладывают их в формат конкретного runtime
→
Проектruntime читает плагины и файлы из своих папок: .claude/, .agents/, .codex/, .opencode/

Требования общие, а инструкции учитывают механизмы runtime. Codex получает собственные TOML-агенты и SKILL.md без перевода промптов Claude; модели берутся из нативных TOML. При установке плагинами скиллы, хуки и MCP приходят из плагинов, а в проект пишутся правила, контракты, память и настройки (в Codex — ещё агенты и каталог выходных блоков). Установщик кладёт всё в папки проекта — туда, где каждый runtime ищет файлы:

ЧтоClaude CodeCodexOpenCode
Правила проектаCLAUDE.mdAGENTS.mdAGENTS.md
Скиллы.claude/skills/.agents/skills/.agents/skills/
Агенты.claude/agents/*.md.codex/agents/*.toml.opencode/agents/*.md
MCP-серверы.mcp.json.codex/config.tomlopencode.json
Контракты профилей.aikit/profiles.json.aikit/profiles.json.aikit/profiles.json
Хукиhooks в .claude/settings.json.codex/hooks.jsonплагин .opencode/plugins/aikit-hooks.js

Подробная матрица с ограничениями — Поддержка runtime.

#Ядро не знает стеков

Главная идея устройства: общие сценарии (/implement-feature, /security-check) не содержат ни одного имени стека или агента профиля. Всё стековое они читают из .aikit/profiles.json — файла, куда установщик собрал контракты подключённых профилей.

Вот фрагмент такого файла для fullstack-проекта, где Nuxt живёт в web/, а бэкенд на Spring (профиль из примера Как добавить стек) — в api/:

json
{
  "profiles": {
    "java-spring": {
      "role": "backend",
      "stack": "Java 21, Spring Boot 3, JUnit 5",
      "agents": {
        "architect": "spring-architect",
        "coder": "spring-coder",
        "tester": "spring-tester",
        "reviewer": "spring-reviewer"
      },
      "commands": { "lint": "./mvnw checkstyle:check", "test": "./mvnw test" },
      "path_signals": ["src/main/java/", "src/test/java/"],
      "root": "api"
    },
    "vue-nuxt": {
      "role": "web",
      "agents": { "architect": "vue-architect", "coder": "vue-coder", "tester": "vue-tester", "reviewer": "vue-reviewer" },
      "commands": { "lint": "npx eslint {files}", "test": "npx vitest run" },
      "path_signals": ["pages/", "components/", "stores/"],
      "root": "web"
    }
  }
}

Поэтому новый стек — это только новая папка в profiles/: ядро править не нужно. Как его добавить — Как добавить стек.

#Что делает /implement-feature

  1. Выбирает профиль. Читает .aikit/profiles.json. Если в задаче есть пути, сравнивает их с root и path_signals: web/pages/orders.vue → профиль с root: web и сигналом pages/. Без путей сопоставляет задачу с role и stack. Если профиль один — берёт его. Если непонятно — спрашивает.
  2. Готовит ветку. Обновляет базовую ветку (main или master; develop, если команда ответвляется от неё) и создаёт от неё ветку задачи по скиллу git-branch. Если в рабочей папке есть незакоммиченные правки — сначала спрашивает, ничего не прячет и не сбрасывает сам.
  3. Архитектор пишет план. Агент agents.architect читает PRODUCT.md, правила своего runtime (AGENTS.md или CLAUDE.md) и похожий код проекта и выводит ARCHITECT_PLAN: какие файлы создать и изменить, какие состояния и ошибки учесть, какие тесты нужны.
  4. Подключает специалиста или пайплайн, если нужно. Если задача подходит под when одного из специалистов профиля, тот дополняет план. Если фиче нужен результат пайплайна, пайплайн идёт здесь.
  5. Кодер реализует план. Агент agents.coder получает ARCHITECT_PLAN и выводит CODER_RESULT — список сделанного.
  6. Тестировщик, ревьюер и линтер работают одновременно. agents.tester пишет тесты по CODER_RESULT, agents.reviewer сначала проверяет код на ошибки, затем по чек-листу профиля, а в это время запускаются lint и format. В Claude Code к ревью добавляется встроенный /code-review.
  7. Проверка тестами. В папке root профиля запускается test.
  8. Исправления. Если ревью нашло критичное или упала команда, задача возвращается кодеру (или тестировщику, если неверен тест). Не больше двух кругов, потом ассистент показывает, что осталось.
  9. Проверка в работе. Если у профиля есть команда run, приложение запускается, и сценарий фичи проходится в браузере или запросами — это скилл /check-feature.
  10. Итог. Ассистент показывает профиль и цепочку агентов, созданные файлы, результат тестов, ревью, проверку в работе и следующие шаги (миграции, ручные проверки).

На любом шаге агент может вернуть вопросы — тогда цепочка останавливается, пока ты не ответишь.

#Как агенты передают работу

Каждый агент выводит результат в оговорённом блоке, следующий получает этот блок на вход:

=== ARCHITECT_PLAN ===
Профиль: vue-nuxt (root: web)
Создать:
  pages/notifications/index.vue — список, фильтр «непрочитанные», empty state
  stores/notifications.ts       — загрузка, markAllRead с optimistic update
Изменить:
  layouts/default.vue           — бейдж с количеством непрочитанных
Тесты: stores/notifications (markAllRead, откат при ошибке)
=== END ARCHITECT_PLAN ===

Кодер не придумывает архитектуру заново, а реализует план. Ревьюер сверяет код с планом и правилами. Так задача не расползается.

#Режимы: --tdd, --no-test и --no-review

Флаги пишутся в начале задачи: /implement-feature --tdd фильтр уведомлений.

ФлагЧто меняется
--tddПосле плана тестировщик пишет тесты на поведение из плана. Они должны упасть, потому что фичи ещё нет. Кодер делает так, чтобы тесты прошли, и сами тесты не меняет
--no-testТестировщик не запускается, новые тесты не пишутся. Команда test профиля всё равно выполняется — существующие тесты должны пройти. Вместе с --tdd не работает: ассистент спросит, какой флаг оставить
--no-reviewРевьюер профиля и встроенный /code-review не запускаются. Исправления идут только по упавшим lint и test

--no-test и --no-review — для быстрых правок, когда важнее сэкономить токены, чем получить тесты и ревью. Их можно указать вместе: /implement-feature --no-test --no-review подпись под кнопкой оплаты — тогда работают только архитектор и кодер, а lint, format и test проверяют результат. Те же флаги есть у /fix-bug: с --no-test тест на баг не пишется, и ничто не поймает баг, если он вернётся.

#Если задача затрагивает несколько профилей

«Добавь эндпоинт заказов и страницу, которая их показывает» — работа и для бэкенда, и для фронтенда. /implement-feature проходит цепочку по каждому профилю: сначала backend — он фиксирует API-контракт, затем web. План бэкенд-архитектора передаётся фронтенд-архитектору, поэтому страница использует ровно тот API, который сделан.

#Специалисты и пайплайны

Четыре роли — обязательная цепочка кода. Кроме неё профиль может иметь два вида дополнительных агентов.

СпециалистПайплайн
Что этоОдин агентЦепочка из нескольких агентов
Когда работаетВнутри цепочки кода, если задача подходит под whenСам по себе, если задача целиком подходит под when и код не нужен; или внутри фичи после архитектора
Что даётСовет: уточняет план для кодераГотовый результат (артефакт): модель, текстура, документ

Примеры на гипотетическом профиле для модов Minecraft с пайплайном asset (арт-директор → моделлер → текстурщик → ревью ассетов):

#Баги и проверка в работе

/fix-bug чинит баг так, чтобы он не вернулся:

Воспроизведениеассистент находит причину и пишет BUG_REPORT: симптом, файл и строка, как воспроизвести
→
Тест на багтестировщик профиля пишет тест, который падает именно из-за бага
→
Фикскодер делает минимальное исправление причины, тест не трогает
→
Проверкаlint, весь test, ревьюер смотрит, нет ли того же бага рядом

/check-feature запускает приложение командой run из контракта и проходит сценарий фичи: в браузере (Playwright MCP или встроенный браузер runtime) для профиля с UI, запросами — для API. Смотрит ошибки в консоли и логах, в конце останавливает приложение. Ничего не чинит — только сообщает, работает ли.

#От идеи до кода

Для крупной фичи есть цепочка до разработки:

/analyze-mvpразбирает идею: аудитория, варианты, риски; пишет документ в docs/mvp/
→
/implement-mvpпревращает документ в технический план: API-контракт, BACKEND и WEB SCOPE, порядок работ
→
/implement-featureреализует каждую часть плана цепочкой агентов профиля

#Хуки — правила, которые соблюдаются всегда

Правило в AGENTS.md или CLAUDE.md модель обычно выполняет, но может и забыть. Хук runtime запускает сам, на каждое событие. AIKit ставит четыре хука. Логика у них одна — скрипт .aikit/hooks/aikit_hook.py, а каждый runtime только вызывает его в своём формате.

КогдаЧто делает хукЕсли правило нарушено
Перед командой или записью файлаНе даёт записать .env и секреты (ключи AWS, токены GitHub, приватные ключи…), добавить .env в git через git add, сделать коммит не по Conventional Commits или с Co-Authored-By, создать ветку не по Conventional BranchДействие отменяется, агент получает причину и исправляет: переписывает сообщение коммита, берёт секрет из переменной окружения
После правки файлаЗапускает format и lint профиля для изменённого файла — в папке root этого профиляЗамечания линтера сразу возвращаются агенту
Когда агент закончил ответЕсли менялся код профиля — запускает его testТесты упали — агент продолжает работу с их выводом. После крупной задачи (8+ файлов) предлагает /capture-memory, если у проекта есть .aikit/memory/
В начале сессииДобавляет в контекст память команды .aikit/memory/INDEX.md и PRODUCT.md, если они заполнены—

Какие файлы считаются кодом профиля, задаёт поле code_extensions контракта: для vue-nuxt это .vue, .ts, .js и родственные, для Python-профилей — .py. Правка README.md линтер не запускает.

После правки файла хук запускает format и lint, только если в команде есть {files}. Команда на весь проект, как ./gradlew compileJava check -x test у forge-1-12-java, на каждую правку слишком долгая: её запускают агенты и /implement-feature.

На Windows хуки запускают команды через cmd.exe. Обёртки ./gradlew и ./mvnw хук запускает через лежащие рядом gradlew.bat и mvnw.cmd.

Хуки ничего не скачивают и не ломают работу: если инструмента нет (например, ESLint не установлен в проекте), хук молча пропускает линтер, а вместо тестов напоминает проверить их вручную. Если сам скрипт упал, действие проходит.

Заметка

Команды хуки берут из .aikit/profiles.json. Поменял там lint или test под проект — хуки запускают уже твою команду.

#Как обновление сохраняет правки проекта

Команды, действия панели (actions) и root в .aikit/profiles.json команда может поменять под себя: например, pnpm vitest run вместо npx vitest run. Чтобы обновление кита не затёрло такую правку, установщик хранит прежние значения кита в .aikit/profiles.kit-defaults.json и при обновлении сравнивает три версии:

Значение в проектеЧто сделает обновление
Совпадает со старым значением кита (команда его не трогала)Заменит на новое значение кита
Отличается от старого значения кита (команда поменяла)Оставит как есть
Команда удалена в проектеНе вернёт
Новая команда, которой раньше в ките не былоДобавит
НазадУстановка и обновлениеДальшеРабота с агентами
